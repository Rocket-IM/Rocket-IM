## 1. 本轮决定什么

本文区分三种状态：**已定约束**来自现有项目文档；**建议基线**是本轮为开展验证提出的默认规则，尚未由产品负责人最终确认；**验证问题**必须由候选方案、协议审查或实际运行回答。建议基线可用于隔离 POC，不直接成为生产默认值。

| 状态 | 内容 |
|---|---|
| 已定约束 | 中心化、单租户、单实例、自托管；独立 Go Service、无 UI Rust 核心、公开 SDK/API；一期完整 21 项、二期 12 项 |
| 已定约束 | Dart/Flutter、Swift、Kotlin、TypeScript 是四种 SDK 语言交付；Flutter 面向 iOS/Android、Swift 面向 iOS、Kotlin 面向 Android，TypeScript 以 macOS、Windows 桌面客户端接入为主、浏览器为次；接入方无需 Rust/Cargo 或绑定生成器 |
| 已定约束 | E2EE、多设备默认开启；按既定策略可关闭；会话创建时固定模式，一期改变模式需新会话；多账号按服务实例隔离 |
| 已定约束 | 四种 SDK 语言交付的 SQLite（包括 TypeScript 桌面与浏览器目标）由 Rust 实现和管理；统一数据库读写线程，浏览器采用等价的串行执行上下文；消息入库提交成功后才派发数据成功事件，宿主通过 SDK 查询数据库 |
| 已定约束 | Rust 统一管理附件编解码、加解密、上传下载及任务生命周期；宿主可配置同时工作的附件数 |
| 建议基线 | 后文的首次信任、设备审批、历史授权迁移、成员历史和数据生命周期规则；数值仅作为 POC 输入或候选产品目标 |
| 验证问题 | 具体密码协议、信任证明格式、PreKey/等效预发布密钥机制、群状态、持久化与恢复、版本和平台支持；SQLite 绑定与浏览器落盘方式、数据库线程分配、附件并发计数口径/作用域/默认值和 codec 支持仍待商议与验证；见第 6、8 节及[端侧存储与附件管理](端侧存储与附件管理.md) |

本轮交付是可评审模型、流程、用例和下一步入口。完成本文不等于完成阶段 0，不勾选路线图的实现或验收项。POC 先验证单聊与群聊安全机制及交付可行性；完整界面、好友业务、附件体验和正式运维在后续阶段实现，仍保留一期归属。

2026-09-15 范围澄清：文中的“四端”是上述 SDK 语言交付简称；TypeScript 交付 SDK API 与对应 Rust 运行产物，桌面运行时和绑定方式尚未选择，不将 Rust 密码核心转译为纯 TypeScript。现有浏览器 WASM、存储、独立锚与重建结果只证明其本机实验范围，不代表 macOS、Windows 桌面 SDK 或桌面安全存储已完成；桌面与浏览器均须遵守相同的身份隔离、事务和提交后事件约束。

## 2. 资产、信任边界与攻击者

### 2.1 谁持有什么

| 资产或状态 | 所有者与可见范围 | 必须满足的约束 |
|---|---|---|
| 业务账号与管理凭证 | 接入方可信业务后台 | 经公开 API 映射为 IM 用户；管理凭证不能下发客户端，不能作为用户密码身份 |
| IM token、设备访问权限 | Service 验证，SDK 按账号持有 | 限定实例、用户、设备和用途；业务登录只取得访问资格，不自动建立设备信任 |
| 设备私钥、会话状态、历史解密材料 | 被授权客户端及其安全存储 | Service、业务服务端 SDK、管理员不得获得；每台设备独立身份，不能复制另一设备私钥充当新设备 |
| 设备公钥、授权证明与版本 | Service 分发，客户端验证和保存可信检查点 | 目录是传递渠道；服务器提供的列表、签名、版本号不自动构成可信结论 |
| E2EE 正文、自定义内容、附件原件及衍生文件 | 授权端侧可见；Service 保存密文 | 文件名、缩略图、封面等能暴露内容的字段按协议保护；附件解密材料走 E2EE 消息 |
| 非 E2EE 内容 | 参与者及有相应权限的服务器处理流程 | HTTPS/WSS、访问控制、保留策略仍生效；界面和公开 API 明确安全模式 |
| 路由与运行元数据 | Service 可观察实例、用户、设备、收发关系、群路由、时间、大小、IP 等 | 消息 ID、游标、投递/已读事件也可能暴露行为；最终按实际字段逐项列明，不能宣传匿名通信 |
| 本地消息、游标、队列、缓存和回调 | Rust 账号引擎统一管理 SQLite 与读写，平台提供必要适配 | 以实例与账号隔离；宿主经 SDK 查询，不直接管理 IM 表；本地明文历史不因传输使用 E2EE 而自动安全，静态加密与密钥保护方案仍待确认 |
| 附件任务、文件及临时产物 | Rust 统一管理处理、传输及生命周期，宿主配置同时工作的附件数 | 任务、文件引用和迟到结果绑定实例与账号；E2EE 原件及衍生物端侧加密；附件文件与 SQLite 不天然构成同一事务 |
| 举报证据 | 用户明确选择后交管理流程 | 只披露确认的内容、对象与上下文；最小权限、保留期限、审计；导出内容不自动证明真实性 |

### 2.2 威胁及保护边界

| 攻击或故障 | 本项目要求验证的结果 | 不得作出的承诺 | 用例 |
|---|---|---|---|
| 窃听、篡改、伪造网络响应 | TLS 校验有效；E2EE 消息的身份、上下文和完整性验证失败时明确拒绝 | TLS 本身不能防恶意 Service | T05、T08、T23 |
| 恶意 Service、公钥目录替换/回滚/分叉 | 已核验身份不能被静默替换；无效授权和已知旧状态被拒绝；分叉检测能力有实验证据 | 只有服务器签名或本地版本号不能证明全局最新、唯一视图 | T03、T04、T18 |
| 凭证被盗、业务后台或管理员失陷 | 单凭访问凭证不能取得已有设备私钥、静默成为可信设备或恢复旧历史 | 被攻陷的业务身份系统仍能破坏账号可用性和非 E2EE 数据权限 | T01、T02、T22 |
| 设备被撤销、群成员被移除 | 排除被撤销方的新密码状态生成的密文，旧秘密不能解密；其旧权限/签名不能复活身份 | 不能收回已保存的副本，也不能保证离线端在现实世界同一瞬间获知撤销 | T13—T17 |
| 恶意群成员 | 非法加人、越权变更、重放和破坏性输入不被诚实客户端接受；错误可解释、资源有上限 | 仍有权限的成员主动把明文或新密钥交给旧成员时，密码协议不能阻止其泄露 | T16、T18、T24 |
| 数据库/备份泄漏、崩溃、状态回滚 | 服务器备份无端侧解密秘密；端侧恢复不重用旧发送状态，不跨账号覆盖 | 加密磁盘不能防已解锁终端被完全控制；删除在线数据不等于抹除所有备份 | T09—T12、T20、T22 |
| 恶意脚本、终端持续失陷、截屏录屏 | 说明客户端分发、宿主代码及运行环境是信任边界；做泄漏检查和失陷恢复验证 | WASM、不可导出密钥或 E2EE 不能阻止有执行权限的恶意宿主读取明文或滥用密钥 | T21、T22、T26 |
| 丢包、压制消息、拒绝服务、流量分析 | 在资源上限内重试或明确失败，显示同步/送达状态 | 不保证恶意服务器诚实持久化、最终投递或隐藏通信关系 | T07、T10、T24 |

可靠投递承诺以按协议运行的 Service 及约定存储/保留条件为前提。恶意服务器能虚报接受、丢弃消息或阻断连接；端侧不能把服务器接受 ACK 当作对方已收到的证明。

## 3. 账号、设备与信任流程

### 3.1 概念与归属

| 概念 | 规则 |
|---|---|
| 实例与用户 | 业务用户标识只在受信业务命名空间中解释；公开映射得到实例内稳定 IM 用户 ID；同名账号或同一 token 不能跨实例复用 |
| 设备 | 一次安装/独立数据空间持有独立身份；设备 ID 不能通过上传相同名称、公钥或复制旧 ID 接管；注册需证明持有对应私钥 |
| 设备访问状态 | 建议区分待授权、可访问、已撤销；由 Service 执行访问限制，未知设备的权限只够完成授权流程 |
| 密码信任状态 | 与在线/登录状态分开；区分未核验、已核验、身份变化/冲突；可信设备授权不能由普通 token 替代 |
| 设备列表与群状态 | 具有可验证授权、前序关系及版本；客户端保存已验证检查点。概念上的版本不是已确定的线协议字段 |
| 历史解密权限 | 与访问状态、未来消息密钥分别授权；新设备登录、进群或通过设备审批都不自动取得旧历史 |

设备审批和撤销请求必须绑定实例、账号、设备公钥、用途、一次性挑战及有效期，防止跨账号转用、重放和替换；联系人核验须绑定准确的实例、身份及当前指纹，不能只比对显示名。具体签名链/凭据格式采用候选方案支持并经审查的机制，不在此定义自研密码算法。

### 3.2 首次设备与首次联系人

1. 业务后台验证账号，经公开接口获取受限 IM 凭证；SDK 在该实例/账号空间生成设备身份并证明私钥持有。
2. 若账号确实没有既有密码身份，建立首次身份记录。已有身份但无设备在线不等于首次注册，必须进入恢复或身份重置流程。服务器声称“首次注册”不能覆盖端侧可信检查点；没有检查点或其他可信依据时，也不能证明它从未有过旧身份，联系人端仍按未核验/身份变化处理，不继承旧信任。
3. 新联系人首次获得的身份标记为**未核验**。建议允许用户明确接受“尚未核验对方身份”的风险后开始交流，并提供通过独立可信渠道比对指纹/二维码的入口；不能标为“已验证”。要求抵抗首次服务器冒充的场景必须先完成独立核验。
4. 核验后保存可信身份关系。后续合法设备添加仍需验证授权连续性；身份无授权地变化、重置或出现冲突时暂停新的 E2EE 发送和密钥分发，提示重新核验，不静默接受服务器的新公钥。

核验信息若只通过同一个可能恶意的 Service 转发，不能独自证明现实身份。首次信任和身份变化的风险提示是建议交互基线，具体指纹与账号级/设备级证明由 Q01 验证后决定。此限制与 [Sesame §6.1](https://signal.org/docs/specifications/sesame/) 对身份核验的边界一致。

### 3.3 新设备授权

1. 新设备登录后生成自己的身份和一次性授权请求，处于待授权状态；显示可供旧设备确认的账号、设备及指纹信息。
2. 现有可信设备经用户确认，为准确的新设备身份生成授权证明。建议 POC 挑战有效期 5 分钟、只能使用一次；到期、取消或字段改变必须重新开始。
3. Service 校验访问权限与当前版本后登记变更；其他客户端验证授权证明和状态连续性，再纳入新的收件设备集合。仅收到 Service 的“授权成功”响应不能跳过端侧验证。
4. 未来消息在状态确认后发给新设备；旧历史须另走第 5 节授权迁移。并发添加/撤销冲突明确拒绝旧版本后重试，不让“最后收到的列表”覆盖可信状态。

建议普通 IM 登录凭证的续期不改变密码信任；本地身份仍在时可重新认证同一设备。单账号退出立即停任务、撤 token 并按策略清理该账号；清除本地身份后再次登录按新设备处理，不能恢复已撤销身份。关闭多设备须指定保留设备，对其余设备执行访问撤销与密码状态更新。

### 3.4 全部设备丢失或身份重置

建议一期先提供旧设备授权迁移，见第 5 节。没有可信旧设备且没有本项目支持、有效的恢复材料时，登录密码重置仅恢复账号访问：明确告知旧历史无法解密，建立新的设备身份代际，废止旧访问凭证，并向联系人暴露身份变化。

新身份不能沿用旧的“已核验”标识，不能自动继承群内密码信任或获得群密钥；原有关系可展示，重新核验/授权后才能恢复相应通信。业务资料显示名不构成身份连续性证明。管理端不能伪造旧设备授权。

## 4. 撤销、群变更与消息状态

### 4.1 三个不同的时点

| 时点 | 意义 | 可对外表达的状态 |
|---|---|---|
| R0：Service 持久化权限变更 | 撤 token、停止连接和领取、拒绝旧版本发送；非 E2EE 访问限制也在此执行 | 访问已撤销；相关密码更新可能仍在进行 |
| R1：诚实客户端验证并提交新密码状态 | 该通信范围的合法发送端已应用排除目标的状态；相关设备/群需分别处理，不能只看账号列表 | 指定通信范围已完成密码更新；无法确认的范围仍待更新 |
| R2：在 R1 状态下生成并持久化新密文 | 本项目旧钥攻击测试的边界，以绑定的状态及协议证据判定 | 只有满足 T13/T16 的实测条件，才能声称旧钥不能解密该密文 |

R0 与 R1 不合并为一个“彻底撤销成功”。旧设备已知的秘密、旧状态下生成的密文和已经解密的内容都无法收回。故意隐瞒变更的服务器可能让不同端长期停留在不同状态；在没有可信新鲜度和一致性证据前，不承诺全局即时撤销。

### 4.2 发送与在途规则

- 新发送前检查已验证的设备/群状态。已知存在撤销或状态冲突时停止生成该范围的新密文，完成新状态同步后再继续；离线端可以保留本地待发送内容，不以旧快照声称已安全发送。
- 已生成并持久化的密文、密码状态、稳定逻辑消息 ID、目标设备集合和状态版本共同保存；普通重试只重发同一条记录，不能为每次网络重试重新加密。
- R0 前已被 Service 接受的旧状态记录保留其原状态和保留期限；只有仍具当前访问权限的接收端可以继续领取，并按协议校验后解密。已撤销设备后续领取始终拒绝，已经取得的副本不能收回；接收展示须能区分历史状态，不能重新标成 R1 后生成的安全消息。
- R0 后提交的旧状态记录由正常 Service 明确拒绝。不得悄悄修改原记录的目标或密码状态；后续需要重发时，旧尝试保持终态，通过明确的重发/替代契约生成新记录。逻辑消息、尝试记录与去重关系由 Q04 锁定并测试，不能重复展示或复活已删除内容。
- 接收方无法仅凭本地时钟证明旧密文是在 R0 前生成还是由旧成员事后伪造。来自已撤销发送身份、无法证明允许接收的旧状态消息应隔离并明确显示失败，不能作为可信新消息接收；更细的历史接受边界由候选协议验证。
- 若发送端被服务器隐瞒了最新撤销，它基于旧状态生成的内容不属于 R2 保护承诺；Q02 必须评估可检测的回滚/分叉与仍存在的延迟边界，不得用“查过服务器最新列表”消除该风险。

### 4.3 群权限与密码状态

Service 验证群主/管理员/成员的业务权限；诚实客户端同时验证群成员变更的密码授权、前序状态和成员集合。建议新人仅能读加入后有权接收的消息，不能自动获赠旧群历史。移除一个用户要排除其所有设备；撤销某设备要更新该设备参与的相关单聊与群密码状态。

并发变更、旧成员再次加人、同版本冲突和非法群状态必须有显式拒绝/恢复流程；不得用重新入群或明文降级自动绕过验证。保留方可能暂时等待状态恢复，但不能把不同成员列表各自通信报为已一致。单聊与群聊的机制、前向安全和失陷后恢复条件分别验证，不能由某个库的单项能力推导整个 IM 已安全。参考 [MLS 架构 §5.3](https://www.rfc-editor.org/rfc/rfc9750.html#section-5.3) 对群状态失配及自动恢复风险的说明；这不代表本项目已选用 MLS。

## 5. 历史恢复与数据生命周期

### 5.1 建议恢复基线

| 场景 | 一期建议行为 | 关键验收 |
|---|---|---|
| 已授权新设备，旧设备可用 | 旧设备明确确认迁移对象及历史范围，经认证加密通道传输仍合法持有的历史材料 | 不经过 Service 明文；目标设备核验；迁移中撤销则终止继续导出 |
| 新群成员 | 默认从加入后的有效状态开始接收 | 不分发加入前解密密钥；不能因拥有群 ID 或附件地址绕过历史限制 |
| 同一用户的新设备 | 独立完成设备授权；可以明确授权迁移本人仍合法持有的旧历史 | 群成员的新加入与同一用户的设备迁移分别校验；不恢复已删除/已失去访问权的服务端内容 |
| 换机、重装、全部设备丢失 | 有可用可信旧设备则迁移；否则按身份重置处理并明确旧历史不可恢复 | 不以密码重置或服务器备份冒充历史恢复；关系保留不自动保留密码信任 |
| 迁移失败、重复或目标空间已有数据 | 先校验再提交；失败保留有效数据，重复不重复导入，账号/实例不匹配拒绝 | 不复制旧设备私钥和正在使用的发送计数/棘轮状态；新设备使用独立未来通信状态 |

加密备份恢复是可选候选方案，当前草案不将其视为已确认必须同时实现的第二条恢复路径。若纳入，须明确用户独立持有恢复密钥、备份包含的历史范围、完整性、反回滚边界、撤销与恢复材料泄漏处理；补充用例后才允许启用。设备授权和历史恢复能力本身仍属于一期，不能移出范围。

保留可解密的本地历史或备份会扩大秘密泄漏后的历史暴露范围；协议对已销毁消息密钥的前向安全，不等于可恢复历史在设备失陷后仍保密。恢复材料不得无验证地还原旧发送状态；如果不能证明状态新鲜度，必须重新建立未来通信状态。完全回滚本地可信状态且没有外部可信检查点时，不承诺自动检测所有回滚。

### 5.2 数值与清理规则

以下均为**建议目标/POC 参数，待产品评审与实测锁定，不是已确认生产容量或默认配置**。自动化使用可控时钟推进期限，不依赖实际等待。

| 项目 | 本轮建议值或规则 | 用途与限制 |
|---|---|---|
| 账号与设备 | 单账号目标最多 5 台设备；单客户端目标同时登录 3 个账号 | 验证上限、并存和关闭多设备；超过限制明确失败，不自动踢出任意设备 |
| 群规模 | 目标 100 个用户、每用户最多 5 台设备 | 候选按最坏 500 个设备身份评估；不是并发/吞吐保证，小组攻击用例先用 3 用户 |
| 密文与附件保留 | 建议接受后 30 天；附件到期不早于引用它的有效消息要求 | 历史接口返回明确过期状态；端侧已有副本按本地清理策略处理；不能过期后仍宣传永久可恢复 |
| 授权请求 | POC 有效期 5 分钟、一次性；旧版本请求冲突失败 | 分别测试到期边界、重放和时钟偏移；授权新鲜度不能仅靠客户端时钟 |
| 账号删除 | 立即停止新访问与待发任务；建议在线数据 24 小时内清理，备份最长 30 天自然淘汰 | 删除关联表、附件可达引用、推送绑定与映射，保留必要非秘密删除标记防复活；已交给其他成员的副本不可收回 |
| 共享数据与举报 | 账号删除不删除其他参与者自己的消息副本；举报建议结案后 30 天清理 | 对未结案和依法需留存的数据由部署方事先配置边界并告知；POC 不使用真实证据 |
| 备份恢复 | 恢复后重放账号/对象删除和权限变更记录，再开放访问；不能只还原旧数据库 | 备份保留与删除标记至少覆盖可恢复窗口；没有可靠新鲜度证明不得恢复旧权限上线 |
| 附件验证样本 | 固定 1 KiB 与 1 MiB 合成文件及衍生文件，测试截断、篡改与取消 | 只验证机制；正式格式、大小、时长、配额与压力指标在附件实现前另锁定 |

减少保留期、改变新人历史或提高规模目标都会影响验收，必须更新对应规则和用例，不得在测试失败后临时降低标准。

## 6. 协议与持久化的最低契约

本节定义行为约束；Q04 的拟议字段、实验接口源、状态及增量结果见[消息协议草案](消息协议草案.md)。`api/` 已有正在验证的 POC 定义和编码样例，尚非正式协议定稿；完整身份/群权限、模式与四端验收通过后才申请关闭对应问题。

| 契约 | 最低要求 |
|---|---|
| 上下文绑定 | 对实例、会话、安全模式、协议版本、发送者/设备、目标和密码状态建立密码可验证绑定，明确哪些字段经关联数据或协议自身认证；不同上下文密文不能串用 |
| 模式与版本 | 创建时固定安全模式；客户端和 Service 均拒绝与模式不符的调用；安全相关元数据不能仅信任服务器提示；不支持版本明确失败 |
| ID 与幂等 | 稳定逻辑消息 ID、每设备密文/尝试记录及其关系明确；同键同内容重试复用结果，同键不同内容冲突失败；整数跨四端无损 |
| 接受/送达/已读 | Service 持久化才接受；接收端校验并持久化才报告对应设备送达；用户已读独立建模；发送到自己的其他设备也应同步 |
| 原子发送 | 密码状态推进和待发送密文共同提交；失败不外发；提交后崩溃恢复同一条记录，不能回退后使用同一密码状态加密不同内容 |
| 原子接收 | 去重、有效消息、密码状态与处理进度一致提交；验证失败不改变有效密码状态、不发成功送达回执，明确记录失败/隔离结果；损坏事件不能永久卡死正常消息队列 |
| 排序与补拉 | 服务端可恢复的排序/游标与提交次序一致；并发提交、分页和推送/补拉交叠不漏消息；安全状态不依赖客户端时间排序 |
| 预发布密钥 | 候选使用 PreKey 或等效机制时，验证身份绑定、签名、领取并发、耗尽、轮换与旧密钥删除；耗尽按已评审协议失败或明确受限，不能自造降级路径 |
| 错误与资源 | 认证失败、信任变化、状态过期、冲突、无法解密和资源超限对调用方可区分；队列、重试、解析、跳过密钥缓存有界；正式名称和限额经 Q04/Q06 锁定 |

### 6.1 正式 SDK 的端侧存储与附件约束

2026-09-14 确认的方向见[端侧存储与附件管理](端侧存储与附件管理.md)，以下是未来实现与验收要求，不改写旧 POC 的加密快照、Relay SQLite 或当前四端内存包的实际能力。

2026-09-15 的[原生秘密保护实验](端侧存储与附件管理.md#15-原生秘密保护与可信配置保存)已在macOS ARM64专用文件钥匙串与SQLCipher上完成局部验证：密钥及可信配置固定、重启保持身份、锁定/缺钥暂停、篡改拒绝和完整结果精确恢复。它没有接入正式SDK，不等同于屏幕锁保护、生产Data Protection或硬件防回滚；helper的合成权威秘密仍按原实验保存，数据库/钥匙串/权威共同回滚仍可能不可检测。

四种 SDK 语言交付的 SQLite（包括 TypeScript 桌面与浏览器目标）由 Rust 持有和管理。数据库读写统一进入专用读写线程，浏览器采用等价的串行执行上下文；如何按 SDK 实例、账号或数据库分配线程/上下文仍待设计。宿主通过 SDK 查询消息与状态，查询与写入遵守相同的隔离和生命周期规则；桌面绑定、浏览器落盘后端、静态加密和平台安全存储方案仍待商议，不能将当前内存包写成已有数据库实现。随后隔离[浏览器存储验证](浏览器存储验证.md)已从普通记录扩展到真实OpenMLS状态与待发送密文共同提交、接收消息/去重/密码状态/处理游标共同提交，以及下载记录/下载游标的独立一致保存；持久未决预约使失败或中断后的密码操作保持阻断。该局部证据尚未整合到四端内存SDK；同库预约不能防全库回滚，秘密保存与安全删除尚未验证，不据此关闭Q05、T09/T10或完整阶段0。随后新增独立锚入口，以 `synthetic_local` 本机锚验证完整旧库阻断及完整候选的精确恢复，见[浏览器存储验证第 7 节](浏览器存储验证.md#7-浏览器独立锚与恢复契约)；生产独立故障域、首次信任和强制可信入口仍未完成。随后在同一本机合成信任边界内增加未决旧范围封存、独立批准的唯一新身份/存储空间与新群互通，结果和限制见[浏览器存储验证第 8 节](浏览器存储验证.md#8-浏览器未决范围安全重建)；生产恢复批准与旧历史迁移不在本项内。

全部数据库读取与写入必须经过 Rust 管理的显式事务，包含单次查询、恢复读取和迁移中的数据/结构读写；同一业务一致性单元共用事务，不能逐条 SQL 独立提交后拼成密码状态或消息结果。读事务正常结束后再交付结果，不让连接、事务或活动游标跨 FFI；失败与取消须可靠收尾，事务状态不明时暂停对应数据空间。SQLite 外的秘密保存、附件文件和独立反回滚锚仍按各自恢复协议处理；初始化与维护命令不默认获得事务外读写例外，具体限制见专项文档。

消息及其持久状态先成功提交，再派发对应数据成功事件。事件在事务结束、相关锁释放后派发，允许宿主在回调中重新调用 SDK 查询，不占用数据库执行上下文等待宿主代码。提交失败可以且必须明确回报错误，但不能伪装成消息入库、有效接收或状态更新成功。关闭、退出、账号切换和订阅取消后，迟到结果仍须核对实例、账号与生命周期归属；成功事件不能让宿主读到尚未提交的数据。此顺序不替代第 6 节的密码状态原子性，也不把本地落盘当作 Service 接受、设备送达或已读。

Rust 统一管理附件编解码、加解密、上传下载和任务生命周期，CPU 处理、网络等待与数据库执行相互隔离；不得持数据库事务或状态锁做长时间编解码、文件处理或网络传输。宿主可配置同时工作的附件数，任务队列、重试、内存和临时磁盘占用也须有界；总数与各阶段的关系、原件与衍生物计数、等待/暂停是否占位、跨账号或跨实例的配置作用域、默认数、线程池及 codec 支持范围均待商议，不能只限制网络请求却无界启动其他处理。

附件文件与 SQLite 记录不天然处于同一事务，必须验证中断后文件与记录的核对、恢复和清理；只有必要文件有效、对应状态提交成功，才能报告附件完成或可用。取消、重试和失败恢复须保留明确结果与有效数据，不重复创建消息或无依据地重新加密；取消不能冒充收回已被 Service 接受的内容。E2EE 原件、缩略图和封面均在端侧加密后上传，解密材料走 E2EE 消息；下载经完整性校验后才标为有效。临时明文须限制访问范围和生命周期，失败、取消、退出与重启清理均按账号处理，不能删除其他任务仍需使用的文件，也不承诺介质级不可恢复擦除。

### 7.2 执行批次与退出

T04/T18 在执行前由 Q02 固定判定条件：对已知低版本或同一前序的可验证冲突，客户端须在生成下一条新密文前报错并暂停；对持续隔离的自洽分叉，必须说明所需的独立可信对照渠道，并验证取得冲突证据后会暂停发送。若采用的方案无法提供该检测路径，问题保持未解决并阻断阶段 0；对照前无法发现的窗口及恢复规则须事先评审，不能只登记“已知风险”就判通过。

1. **候选筛选：**先做 Q01/Q03 的资料与许可证核查、原生与浏览器最小构建，按相同标准淘汰不满足硬约束的候选。未使用的候选不加入正式依赖。
2. **身份与会话：**T01—T08、T11，取得身份授权、离线首条和错误处理证据。
3. **持久化与变更：**T09—T10、T12—T18、T20—T21，验证最易迫使架构返工的状态问题。
4. **边界与交付：**T19、T22—T26。四端构建探索可与前两批并行，最小 Release 包实际运行必须在阶段 0 内完成，不能拖到阶段 3 首次验证。

每批失败先定位模型、协议、实现或测试装置原因，保留失败证据，不删除用例换取通过。功能仍需后续完整 Service/SDK、实际平台和完整一期验收；POC Relay 的模拟故障不能替代正式数据库事务、系统推送或容量实测。

Q04 已接入签名群移除/同账号设备撤销及候选恢复。固定 Service 回执公钥后，客户端验证终态和实际 MLS 变更，保留尚未完成的原意图；补齐已知恢复水位后才能重新准备或发送。失败候选不回退已消耗的密码发送状态，每 epoch 新候选上限为 64；初始信任仍来自 fixture。

R1 后已能接收变更前正常 Service 接受的限定旧消息，最多保留 2 个过去 epoch。首次接收必须有精确消息接受证明和本地已验证的历史检查点，双方当前仍获授权且公钥未变；接收成功不回退当前发送状态。无历史证据或已撤销发送者的未接收旧消息明确隔离，不能用 Service 签名授予历史访问。该签名不证明实际接受时间，也不解决恶意双签、分叉和回滚，完整 Q02 仍未完成。

新成员已通过真实 Add/Welcome 接入实验权限链。初始身份仍用独立 fixture 固定；群主邀请新账号设备，同账号新设备由当前群内有效旧设备签名批准，历史策略均限于 `from_join`。新设备验证公开授权链及实际 Welcome 后建立首个本机 R1，过去 epoch 为空；后续才从真实加入后的变更积累历史。群范围信任不导入全账号 roster，登录凭证、群主身份或旧本地 roster 授权不能替代新的群设备批准。材料仅原目标当前有权时可领取，失败不消耗有效 KeyPackage 或部分改写状态。`join_enabled=0` 的旧实验服务库仍禁用两种新增；旧客户端快照缺完整设备公钥历史时显式拒绝新的 AddDevice。随后已接通单群、同账号的选定历史副本迁移：源端只从正常收件记录提取仍持有的正文与精确接受证明，独立 HPKE 加密给目标；目标核对请求、源签名、Service 接受及全部副本后原子导入。副本明确标记为旧端负责的 `source_authenticated_copy`，不声称目标已重新验证原作者 MLS 正文，也不带入旧身份私钥、密码状态或游标。源/目标已知撤销、当前检查点变化、过期、取消和内容冲突均拒绝，失败保留有效状态。正常 Service 在提交/领取前检查原消息仍可用；既有接受回执不是新的在线领取授权，离线目标不能据此发现尚未知晓的删除或撤销。具体边界见[消息协议草案第 15 节](消息协议草案.md#15-已接收历史副本的授权迁移)。

本轮已补齐发送接受证明：只对本机精确原 outbox 尝试核验固定 Service 签名并原子保存，迟到原接受会阻止其他尝试继续发送，不回滚已有密码或尝试状态。该事实可在权限暂停/失权后补记，但不能解除暂停或授予历史访问。已发送副本复用原定向迁移；Service 精确原 sender 不要求不存在的自身收件事件，其他来源仍须通过原收件事件检查。目标保持原收件/发送一致性，副本不替本机补 ACK，不等于新增聊天消息，详见[消息协议草案第 16 节](消息协议草案.md#16-已发送历史的接受证明与迁移)。

Q02 已补齐本机已知回滚和同前驱分叉检测：检查开始先持久阻断新加密；有效冲突证据与暂停一起保存，重启不能解除；回滚/追链须显式恢复且不清原权限暂停，已证实分叉不能原地解除。无独立对照时 `freshness=unknown`；生产对照渠道仍未实现；全快照回滚新增的本机独立锚实验见下文，完整 Q02 仍开放。契约、F01—F12 及实际结果见[消息协议草案第 17 节](消息协议草案.md#17-q02-已知回滚与同一前驱分叉的检测)。本轮进一步固定人工带外逐次核验的契约，完成实际持有端导出、双端签名绑定的离线公开交换、可信前驱对照及取消/撤销/原子退出本机验证；自动化均为 `synthetic_local`，不能证明生产独立性或全局最新，详见[协议第 18 节](消息协议草案.md#18-q02-独立对照的最小信任契约与本机交换)。附件、全账号跨群设备授权及完整恢复流程仍未完成。旧钥验证的访问限制仍单独记录，不将普通网络一致性测试作为旧钥安全证明。

阶段 0 出口仍以路线图为准：安全模型、协议及许可证决策完成评审，核心攻击测试和四端最小包运行通过；关键未知风险解决，剩余风险有实际责任人与处理方案。本文的建议数值、信任交互、历史恢复与保留规则在对外承诺前必须完成评审。本次已完成的[出口差距评审](开发路线与检查清单.md#阶段-0-出口差距评审2026-09-14)统一列出已验证、未验证与关闭条件，结论为阶段0仍未通过。该次评审所列“下一项最小补测”是当时的建议；随后已按授权开展隔离浏览器普通记录及真实OpenMLS持久化实验，后续执行与剩余边界见[浏览器存储验证](浏览器存储验证.md)，不沿用“尚未启动”描述当前进度。

## 10. 设计参考

以下官方资料于 2026-09-09 查阅，仅支持边界分析，不代表已采用其协议或证明本项目安全。依赖许可证、版本与平台支持另按 Q03 实时核查。

- [W3C Web Crypto：作者安全注意事项](https://www.w3.org/TR/webcrypto/#security-considerations-for-authors)：脚本注入、同源存储和密钥对象的使用权限边界；据此要求 T26 记录宿主脚本及更新渠道的信任范围。
