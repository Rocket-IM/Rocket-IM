## 2. 资产、信任边界与攻击者

### 2.1 谁持有什么

| 资产或状态 | 所有者与可见范围 | 必须满足的约束 |
|---|---|---|
| 业务账号与管理凭证 | 接入方可信业务后台 | 经公开 API 映射为 IM 用户；管理凭证不能下发客户端，不能作为用户密码身份 |
| IM token、设备访问权限 | Service 验证，SDK 按账号持有 | 限定实例、用户、设备和用途；业务登录只取得访问资格，不自动建立设备信任 |
| 设备私钥、会话状态、历史解密材料 | 被授权客户端及其安全存储 | Service、业务服务端 SDK、管理员不得获得；每台设备独立身份，不能复制另一设备私钥充当新设备 |
| 设备公钥、授权证明与版本 | Service 分发，客户端验证和保存可信检查点 | 目录是传递渠道；服务器提供的列表、签名、版本号不自动构成可信结论 |
| E2EE 正文、自定义内容、附件原件及衍生文件 | 授权端侧可见；Service 保存密文 | 文件名、缩略图、封面等能暴露内容的字段按协议保护；附件解密材料走 E2EE 消息 |
| 非 E2EE 内容 | 参与者及有相应权限的服务器处理流程 | HTTPS/WSS、访问控制、保留策略仍生效；界面和公开 API 明确安全模式 |
| 路由与运行元数据 | Service 可观察实例、用户、设备、收发关系、群路由、时间、大小、IP 等 | 消息 ID、游标、投递/已读事件也可能暴露行为；最终按实际字段逐项列明，不能宣传匿名通信 |
| 本地消息、游标、队列、缓存和回调 | Rust 账号引擎统一管理 SQLite 与读写，平台提供必要适配 | 以实例与账号隔离；宿主经 SDK 查询，不直接管理 IM 表；本地明文历史不因传输使用 E2EE 而自动安全，静态加密与密钥保护方案仍待确认 |
| 附件任务、文件及临时产物 | Rust 统一管理处理、传输及生命周期，宿主配置同时工作的附件数 | 任务、文件引用和迟到结果绑定实例与账号；E2EE 原件及衍生物端侧加密；附件文件与 SQLite 不天然构成同一事务 |
| 举报证据 | 用户明确选择后交管理流程 | 只披露确认的内容、对象与上下文；最小权限、保留期限、审计；导出内容不自动证明真实性 |

### 2.2 威胁及保护边界

| 攻击或故障 | 本项目要求验证的结果 | 不得作出的承诺 | 用例 |
|---|---|---|---|
| 窃听、篡改、伪造网络响应 | TLS 校验有效；E2EE 消息的身份、上下文和完整性验证失败时明确拒绝 | TLS 本身不能防恶意 Service | T05、T08、T23 |
| 恶意 Service、公钥目录替换/回滚/分叉 | 已核验身份不能被静默替换；无效授权和已知旧状态被拒绝；分叉检测能力有实验证据 | 只有服务器签名或本地版本号不能证明全局最新、唯一视图 | T03、T04、T18 |
| 凭证被盗、业务后台或管理员失陷 | 单凭访问凭证不能取得已有设备私钥、静默成为可信设备或恢复旧历史 | 被攻陷的业务身份系统仍能破坏账号可用性和非 E2EE 数据权限 | T01、T02、T22 |
| 设备被撤销、群成员被移除 | 排除被撤销方的新密码状态生成的密文，旧秘密不能解密；其旧权限/签名不能复活身份 | 不能收回已保存的副本，也不能保证离线端在现实世界同一瞬间获知撤销 | T13—T17 |
| 恶意群成员 | 非法加人、越权变更、重放和破坏性输入不被诚实客户端接受；错误可解释、资源有上限 | 仍有权限的成员主动把明文或新密钥交给旧成员时，密码协议不能阻止其泄露 | T16、T18、T24 |
| 数据库/备份泄漏、崩溃、状态回滚 | 服务器备份无端侧解密秘密；端侧恢复不重用旧发送状态，不跨账号覆盖 | 加密磁盘不能防已解锁终端被完全控制；删除在线数据不等于抹除所有备份 | T09—T12、T20、T22 |
| 恶意脚本、终端持续失陷、截屏录屏 | 说明客户端分发、宿主代码及运行环境是信任边界；做泄漏检查和失陷恢复验证 | WASM、不可导出密钥或 E2EE 不能阻止有执行权限的恶意宿主读取明文或滥用密钥 | T21、T22、T26 |
| 丢包、压制消息、拒绝服务、流量分析 | 在资源上限内重试或明确失败，显示同步/送达状态 | 不保证恶意服务器诚实持久化、最终投递或隐藏通信关系 | T07、T10、T24 |

可靠投递承诺以按协议运行的 Service 及约定存储/保留条件为前提。恶意服务器能虚报接受、丢弃消息或阻断连接；端侧不能把服务器接受 ACK 当作对方已收到的证明。

## 3. 账号、设备与信任流程

### 3.1 概念与归属

| 概念 | 规则 |
|---|---|
| 实例与用户 | 业务用户标识只在受信业务命名空间中解释；公开映射得到实例内稳定 IM 用户 ID；同名账号或同一 token 不能跨实例复用 |
| 设备 | 一次安装/独立数据空间持有独立身份；设备 ID 不能通过上传相同名称、公钥或复制旧 ID 接管；注册需证明持有对应私钥 |
| 设备访问状态 | 建议区分待授权、可访问、已撤销；由 Service 执行访问限制，未知设备的权限只够完成授权流程 |
| 密码信任状态 | 与在线/登录状态分开；区分未核验、已核验、身份变化/冲突；可信设备授权不能由普通 token 替代 |
| 设备列表与群状态 | 具有可验证授权、前序关系及版本；客户端保存已验证检查点。概念上的版本不是已确定的线协议字段 |
| 历史解密权限 | 与访问状态、未来消息密钥分别授权；新设备登录、进群或通过设备审批都不自动取得旧历史 |

设备审批和撤销请求必须绑定实例、账号、设备公钥、用途、一次性挑战及有效期，防止跨账号转用、重放和替换；联系人核验须绑定准确的实例、身份及当前指纹，不能只比对显示名。具体签名链/凭据格式采用候选方案支持并经审查的机制，不在此定义自研密码算法。

### 3.2 首次设备与首次联系人

1. 业务后台验证账号，经公开接口获取受限 IM 凭证；SDK 在该实例/账号空间生成设备身份并证明私钥持有。
2. 若账号确实没有既有密码身份，建立首次身份记录。已有身份但无设备在线不等于首次注册，必须进入恢复或身份重置流程。服务器声称“首次注册”不能覆盖端侧可信检查点；没有检查点或其他可信依据时，也不能证明它从未有过旧身份，联系人端仍按未核验/身份变化处理，不继承旧信任。
3. 新联系人首次获得的身份标记为**未核验**。2026-10-09 已确认首轮先独立核验、按设备身份核验：准确核验事实持久化后，才允许面向该设备的新的 E2EE 发送和密钥分发。接受未核验风险不能放行或标为“已核验”。对应门禁已在隔离 POC 实现，运行范围见 3.2.2；正式 SDK 尚未接入。
4. 核验后保存可信身份关系。后续合法设备添加仍需验证授权连续性；身份无授权地变化、重置或出现冲突时暂停新的 E2EE 发送和密钥分发，提示重新核验，不静默接受服务器的新公钥。

核验信息若只通过同一个可能恶意的 Service 转发，不能独自证明现实身份。首轮核验对象已确定为设备身份；具体公开对象编码、指纹格式和核验入口在对应 POC 实施时固定并验证。此限制与 [Sesame §6.1](https://signal.org/docs/specifications/sesame/) 对身份核验的边界一致。

标准依据只约束身份绑定责任：MLS BasicCredential 是身份声明，应用仍须验证预期身份与签名钥的绑定；恶意认证方能够伪造绑定。[RFC 9420 §5.3](https://www.rfc-editor.org/rfc/rfc9420.html#section-5.3)、[§5.3.1](https://www.rfc-editor.org/rfc/rfc9420.html#section-5.3.1)、[§16.10](https://www.rfc-editor.org/rfc/rfc9420.html#section-16.10)。MLS 架构允许应用采用凭据体系或独立指纹核验，初始 Basic KeyPackage 自身不建立可信身份绑定。[RFC 9750 §4](https://www.rfc-editor.org/rfc/rfc9750.html#section-4)、[§8.4.2](https://www.rfc-editor.org/rfc/rfc9750.html#section-8.4.2)。下面是本项目已确认的首轮契约，3.2.2 单独记录其局部运行证据。

**信任事实的来源与范围。**

| 事实 | 必须取得的依据 | 不授予的能力 |
|---|---|---|
| 业务账号访问 | 受信业务系统映射的实例内账号及受限凭证 | 设备私钥持有、联系人独立核验、旧历史解密 |
| 设备私钥持有 | 正常 Service 对一次性挑战验证设备签名；绑定实例、账号、设备、公钥、用途、挑战及有效期 | 现实身份核验、账号历史连续性；恶意 Service 的“验证成功”也不能独自说服联系人 |
| 联系人独立核验 | 用户通过独立可信渠道核对预期联系人、实例、账号及准确密码身份；返回绑定该对象的确认 | 全账号其他设备、其他实例或变化后的身份自动获信任 |
| 已有设备授权 | 当前可信前驱的有效授权及完整适用范围、版本与成员链 | 新设备自动成为独立核验对象；群内授权扩展到全账号；旧历史自动迁移 |
| Service 声明 | 单独固定的 Service 回执钥及有效签名 | 联系人身份真实性、私钥持有或全局唯一新鲜视图 |

注册挑战需由验证方生成，限制用途和期限；成功消费与设备绑定共同提交，重复完成同一绑定返回原结果，换公钥、换账号、过期和重放不得建立新绑定。复制旧设备 ID、公钥或持有同一个 token 不能接管原身份。仅持有凭证而没有私钥的攻击者仍可能取得密文或元数据，不能把“无法解密”写成“无法下载”。该风险及签名挑战缓解见 [Sesame §6.3](https://signal.org/docs/specifications/sesame/#protecting-server-communications)。正式挑战格式、凭证生命周期和 HTTP 接口尚未实现，实施前须固定实验契约与向量。

| 项目 | 已确认规则 | 适用范围 |
|---|---|---|
| 首次未核验发送 | 先独立核验；未核验时拒绝新的 E2EE 发送和密钥分发，风险接受不放行 | 核验事实成功保存且其他门禁有效后，才允许准确对象与通信范围的操作；不降级明文 |
| 核验对象 | 按设备身份核验，绑定实例、稳定账号 ID、设备 ID、身份签名公钥及身份代际（若有） | 全部收件设备逐一满足；合法新增设备的授权连续性与独立核验分别记录，不继承其他设备的核验 |

新增设备需核对新的设备身份对象；首轮不建立账号级身份锚或未核验风险接受放行入口。每台设备保留独立密码身份，单群不得出现重复签名钥。[RFC 9420 §16.7](https://www.rfc-editor.org/rfc/rfc9420.html#section-16.7)。独立核验需同时核对身份和钥，单独比对一串指纹可能绑定到错误联系人。[X3DH §4.8](https://signal.org/docs/specifications/x3dh/#identity-binding)。

**信任记录与状态转换契约。** 核验事实由 Rust 的实例/账号数据空间持有，宿主只发起查询与确认。记录保存已接受绑定、当前候选、核验依据及版本，身份冲突时保留旧绑定和新候选，拒绝静默覆盖。POC 的实际存储和状态范围见 3.2.2。

- 当前设备对象的核验状态采用互斥状态：未核验、已核验、身份变化/冲突。首轮没有风险接受放行分支；风险接受不能把未核验转换为已核验。
- 历史依据单独记录为未知、连续、缺口或显式重置。无本地记录且无可信前驱依据时为未知；已知曾有可信前驱却缺少授权链时为缺口。没有本地联系人记录不等于远端从未有密码身份；Service 声称“首次注册”不把未知或缺口转为连续。首次未知可经独立核验建立当前绑定并按有效权限开展新的通信，过去连续性仍未知，不能继承旧信任或补造授权链。
- 从 Service 获得首次候选只进入未核验。只有独立核验确认准确对象后才进入已核验；拒绝、取消、信息不完整或保存失败均不发布已核验成功。
- 已有绑定遇到设备身份签名公钥、身份代际或账号绑定改变，进入变化/冲突并暂停相关新的 E2EE 发送和密钥分发；重复收到完全相同的候选或确认保持幂等。无效或缺失授权不成为合法替换依据。正常 MLS epoch、ratchet 或同一身份签名的合法 KeyPackage 更新不改变该身份绑定，不自动触发重新核验；材料有效性仍按原协议检查。
- 合法新增设备分别记录其授权链和核验事实，独立核验前保持未核验并阻断面向该设备的新发送和密钥分发。新设备登录、入群、收到签名目录或业务重置密码均不自动继承旧核验及历史权限。
- 显式身份重置另行确认新对象、保存旧身份终态并重新核验；不能恢复已撤销设备、旧群权限或旧历史。全部可信材料共同回滚仍受独立锚边界限制。

核验展示对象至少包含格式版本、实例、预期联系人及稳定账号 ID、设备 ID、身份代际（若有）和完整身份签名公钥；指纹或二维码必须绑定同一对象。首轮验收可独立交换完整公开对象，摘要/编码格式须在实施时固定并提供向量，不新增密码算法。独立渠道的真实性是外部输入假设，测试控制器的可信输入不能写成真实用户已核验。

确认请求还必须绑定本地实例、账号、设备/引擎生命周期、当前候选的完整身份和记录版本。用户看到对象后发生换钥、换账号、关闭或重新初始化、候选版本更新时，迟到确认明确拒绝；不能只携带远端设备 ID。跨设备同步核验事实需另有可验证来源，本轮不设计自动同步。

**旧数据、多目标与重试边界。**

- 旧 POC 快照的 pin 和群 checkpoint 记录固定公钥及授权事实，没有独立核验来源。迁移时保留旧绑定、有效历史和原门禁；缺少可验证核验事实的对象保持未核验，不能按字段存在、旧测试通过或既有群成员身份自动补成已核验。新增核验字段须固定格式版本，分别验证旧快照升级与旧程序读取边界；拒载不自动清除锚预约。
- 新发送按当前完整授权收件集合逐设备检查核验事实，包含本账号其他收件设备。任一目标未核验时明确阻断整份新加密，不静默过滤设备或返回部分成功；核验后、执行前目标或身份变化需重新检查或拒绝，目标集合变更须走原授权协议。MLS 群中只停止向某设备投递，不能证明仍在群内的该设备无法解密。
- 密钥分发单独检查目标设备的核验事实，包含授予设备群秘密的 Welcome 和新增密钥材料生成、导出及外发。合法设备授权不能替代核验；未核验目标不得提前获得秘密，返回已保存材料也不自动授予外发许可。
- 已保存 outbox 原尝试与新加密、新后继分别处理。允许原尝试重发时只能复用原头、密文、目标和 ID，不能按新 pin 重加密、改收件人或删除旧记录。读取/恢复原件不授予外发许可，原件重发须核对原身份/目标对应的核验事实及既有权限、Q02 和锚门禁，新身份的核验不授权旧身份原件外发。已回收原件继续返回紧凑终态/“内容已回收”，不能为重试重新造出密文；已交付的副本无法收回。

**操作门禁与持久化。** 核验状态、授权链、业务访问、Q02 一致性和独立锚恢复分别检查，发送许可由全部适用条件共同决定。

| 状况 | 已确认的首轮结果 |
|---|---|
| 当前对象未核验，其他条件有效 | 新发送和密钥分发明确拒绝；原门禁许可的查询/核验操作可用，不能显示已核验 |
| 当前对象已核验且所有适用条件有效 | 允许该对象、该通信范围的新 E2EE 操作；不因此获得旧历史 |
| 身份变化、授权无效或历史缺口未处理 | 暂停相关新发送/密钥分发，返回具体原因；保留有效旧记录和候选供处理 |
| 权限未决、访问移除、Q02 暂停或独立锚未完成 | 独立核验不解除原门禁；只允许各恢复协议已经许可的查询/确认操作 |

现有权限门禁允许部分 pin 元数据操作，Q02 暂停则拒绝 pin；这不代表两者允许发送。后续接入应复用原门禁，禁止用核验或重置命令清除权限未决、一致性暂停或锚预约。

核验记录和对应操作结果成功持久化后才交付成功。普通模式提交前失败保留旧状态；提交后输出丢失，重启查询恢复已提交的准确事实，重复确认不能改绑。启用独立锚时遵循原预约、保存、Finish 和精确恢复顺序，未决预约继续阻断相关密码操作；仅有完整匹配的恢复日志时才能精确 Finish，保存后缺日志或日志不匹配则保持 `anchor_unresolved`，不能因文件已保存而导出核验成功事实。核验事实恢复不证明整库回滚安全。正式 SDK 的读写均经 Rust 显式事务，不能由宿主另建联系人信任数据库。

### 3.2.2 Q01 最小运行 POC 与验证边界（2026-10-09）

**结论：从 `fa8bf03` 实施的注册私钥持有证明、逐设备核验事实及发送/密钥分发门禁达到限定 `PASS_SCOPED`；原专项回归仍有两项修改前已存在的失败。** 实验继续使用 Rust 密码探针、Python Relay 和本机合成装置。完整 Q01、T01/T03 与阶段 0 保持 `NOT_COMPLETE`；本轮没有修改正式 Go Service、四端 SDK 包或界面。

#### 注册与核验入口

| 入口 | 实际行为与归属 |
|---|---|
| HTTP `begin_device_registration` / `complete_device_registration` | Bearer 决定实例内主体，Relay 生成一次性挑战；公开 Rust 验证器验证设备签名，公钥绑定、挑战消费及固定结果在原 SQLite 写事务共同提交 |
| Rust `device_registration_prove` | 本机私钥签署准确挑战原字节；检查声明的实例、账号、设备和公钥，不改变 MLS 状态 |
| `identity_trust_observe` / `identity_trust_inspect` | 候选只建立未核验或持久变化状态；只读查询准确事实，不授予发送权限 |
| `identity_trust_prepare` / `identity_trust_confirm` / `identity_trust_reset` | 原 Rust 进程的有界 `--session` 模式持有展示生命周期；确认核对独立公开对象，重置保存旧绑定并使新对象未核验，之后需单独确认 |

注册声明版本为 `rim-device-registration-1`，包含实例、账号、设备、注册 ID、公钥、`register_device` 用途、32 字节随机挑战及签发/到期时间。时间用 UTC Unix 毫秒的规范 u64 十进制字符串，期限为 300000 毫秒，原声明最大 4096 字节。签名域为 `Rocket-IM/POC/device-registration/v1` 后接一个零字节；签准确原字节。首次接受在验签后再次检查期限；同一已提交证明可取回原结果，仍先检查当前撤销状态。换钥、跨主体或第二挑战不能建立同一成功绑定。

公开设备对象版本为 `rim-device-identity-1`，绑定 `service_id`、`account_id`、`device_id` 和完整 `signature_key`，本轮没有账号级身份代际。指纹是 [公开对象](../poc/openmls-probe/src/identity_trust.rs) 的固定字段 JSON 与 `Rocket-IM/POC/device-identity/v1` 加零字节域的 SHA-256，输出小写十六进制；联合验收独立交换完整对象。展示还绑定观察者完整身份、记录版本、用途、Rust 会话随机值和展示随机值，`previous` 必须存在，可为 `null`。宿主不能指定会话随机值；切换实例/账号/设备、关闭重开使旧展示失效，候选版本变化拒绝迟到的新确认；已提交的准确原确认/重置保留幂等，不改变绑定。

来源实现见 [Rust 注册](../poc/openmls-probe/src/device_registration.rs)、[Relay 注册](../poc/network-relay/device_registration.py)、[核验记录](../poc/openmls-probe/src/lab/identity_records.rs)及[会话](../poc/openmls-probe/src/lab/identity_session.rs)。HTTP 和公开类型仍属 [POC OpenAPI](../api/http/poc.openapi.json) 与 [POC schema](../api/realtime/message.schema.json)，不是稳定产品 API。

#### 持久化、外发与兼容

- Rust 使用原加密快照共同保存核验记录和密码状态，原 16 MiB 快照限额保留；核验账本最多 128 个目标、1024 个退役绑定、1 MiB。实际状态为 `unverified`、`verified`、`changed`，历史依据为 `unknown`、`gap`、`reset`；装置不生成全账号连续性证明。Relay 注册账本限 128 条、每设备 32 条、2 MiB，开始时预留完成结果空间。这些是实验硬限额，缩小字节预算负例不代表自然达到生产容量。
- 新初始化显式保存核验格式 v1。真实旧程序产生的字段缺失快照可以加载，但旧 pin/checkpoint 不成为核验；准确核验后只允许原门禁许可的操作。旧程序拒绝新初始化和已核验快照，原快照保持。Relay schema 7 升为 8，旧公钥不补造成功注册，缺失新标记/表明确拒绝；旧 Relay 拒绝新格式且不修改数据库。
- [门禁](../poc/openmls-probe/src/lab/identity_gate.rs)覆盖新群/缓存 Welcome、新发送、Add/Device 准备及缓存、历史包生成与缓存外发。新发送检查完整当前收件设备，包含本账号其他设备；任一未核验目标使整次新加密拒绝。Q01 的确定性元数据拒绝在锚预约前检查，执行时再次检查。
- 原 outbox 重发使用原头、ID、密文和目标；签名权限路径从已保存的准确原检查点取得目标，缺证据阻断。新身份核验不授权旧身份原件外发；M12 已回收原件仍只返回紧凑终态。原权限、Q02 和锚门禁保留，公开权限/一致性诊断查询不导出 Welcome、历史包或正文，也不清除暂停。

目录候选与可信事实分开保存。每个目标必须能查出候选来源、已验证前驱/证据、完整身份绑定、访问/撤销状态、核验状态及新鲜性依据；Service 不得直接下发可被采信的 `verified=true`。首次无前驱保持未知，经准确独立核验可建立当前设备绑定，不能据此宣称完整账号目录已获信任。未验证或缺链候选不得用于新的密钥分发。

最小 POC 建议使用有界**完整快照**，成功验证后原子替换目录候选；失败保留有效快照，缺项不自动删除本地核验/撤销墓碑或群成员。已有可信版本遇旧版本拒绝回退，同版本异摘要持久记录冲突；高版本无证据不能清除暂停。材料库存单独版本化，补充同身份材料不改变设备身份或核验结果。分页/增量暂不引入，未来扩展必须绑定同一快照和连续游标。

首轮目录只验证正常 Service 的版本/撤销一致性、恶意输入下的准确绑定及**已知**回滚/分叉；无独立新鲜性依据仍标为未知，不把第 17—18 节的单群 Q02 对照外推成全账号证明。POC 的初始授权来源继续明确为合成独立装置。真实全账号目录的首次授权主体、授权链格式和生产独立新鲜性来源尚待专门收敛，不在本项伪造新账号根或上线完整身份系统。

以下为建议的最小契约；字段及操作边界统一见[协议第22节](消息协议草案.md#22-q01-设备目录与-keypackage-生命周期草案2026-10-14)。

1. **生成与发布。** Rust 先持久保存新 bundle、公开原字节及发布意图，再外发公开材料；批量发布全成或全败。每份新包使用新的 init/leaf 加密钥，身份签名钥保持；Service 验当前主体/注册、公钥与材料签名、有效期、套件和配额，不接收私钥。发布丢响应只查询/重试同一原件，不能再生成材料当作重试；已退役/已分配的同一材料不能换发布 ID 复活，也不能重签期限、改变编码后复用同一 init 公钥绕过原字节摘要唯一性。
2. **领取即退出公共池。** 领取前保存准确请求，绑定邀请设备、目标完整身份、目录依据、已有会话与合法加入动作；凭证和该动作权限均须验证。正常 Service 在同一事务选出一份有效未分配材料、固定领取结果并使其不再可分配，提交后才返回。不同请求并发争一份时最多一份成功；同一幂等请求只得相同结果。第一次明确耗尽也保存该请求的终态，补充后以新请求表达新的尝试。
3. **不把领取当成入群。** 领取不是群授权接受，也不是目标已经消费私钥。群变更仍按原 Proof/Commit/回执流程；拟议新版本须将领取证据、准确目标及材料原件一同绑定到候选。一次材料最多对应一个被接受加入结果。无关请求、另一群或另一目标即使持有材料也不得抢用。
4. **丢响应与冲突。** 发布、领取、权限候选、Welcome 本地应用均保存各自的原请求与结果；网络超时或未查询到记录不等于“未提交”。有效期内的精确重试复用原件。取消、过期或确定失败的已分配材料退役，不退回公共池；终态不明时保留未决，不重新生成 Commit/Welcome 或改领材料来绕过。原权限/锚恢复协议继续有效，不清预约、旧 outbox 或旧候选解决不确定提交。
5. **首次加入提交。** 目标检查当前身份/访问、完整权限链、自己的材料、实际 Welcome 发送者与群状态后，共同提交 bundle 消费、群状态与精确成功结果；失败不消耗有效本地 bundle、不产生半群状态。成功后的精确重试只返回已保存结果，不重跑 Welcome、不回退后续通信状态。
6. **到期与同身份轮换。** 发布、首次领取、首次群接受、首次本地加入均重查材料有效性；时钟异常明确失败，不关闭库校验。允许提前补充同身份新材料；退役旧材料须与领取串行裁决。普通 MLS 更新和新 KeyPackage 的 init/leaf 钥改变不触发联系人重核验，身份签名钥/绑定/代际变化则必须暂停并单独重新核验。
7. **撤销与旧材料。** R0 同事务撤访问并关闭该身份全部未完成材料的新领取/新接受资格，已分配材料不复活。撤销与领取/接受竞争必须有唯一事务顺序；先撤销则拒绝，先领取但尚未接受仍受撤销阻断。既有接受事实可以保留，但不是撤销后的材料外发或新加入许可。客户端知道撤销后拒绝旧材料；隐瞒撤销的恶意 Service 仍受第 4 节及 Q02 边界约束，不能宣称全局即时防御。

第 13—14 节旧 POC 在权限竞争后可保留同一 KeyPackage 重新准备 Welcome，且没有领取账本。本轮建议首版领取契约绑定一个准确候选；该候选确定封口/失败后退役材料，再由新材料形成新候选。此变化已在 22.7—22.8 新协议与恢复/兼容场景中验证，不重解释旧协议或旧材料。已被接受但到期未能首次加入的记录继续保留；补充材料不自动撤销旧群成员再邀请。旧设备重新入群仍未实现；下文及协议 22.9 提出专用恢复建议，不能给出“补充后必能恢复原邀请”的承诺。

#### 已接受邀请过期的恢复安全边界（2026-10-14）

**契约分析、隔离机制及动作/唯一后继契约固化已完成；后续最小业务 POC 见协议 22.9.11，完整业务恢复尚未验收。** 推荐流程、锁定 OpenMLS 的静态依据、现有实现改动点、E01—E18 完整业务待验矩阵及 22.9.9 机制实测统一见[协议 22.9](消息协议草案.md#229-已接受邀请首次加入过期的恢复契约2026-10-14)，不重复维护第二份验收表。

- **原接受不可撤回。** Service 的原 R0、成员历史、材料占用及原消息接受保持；目标未回 ACK 不能证明任何副本都没有加入。健康本机已有 joined_record/R1 时只做精确查询与补链，材料 TTL 不使已建立会话失效；提交不明先恢复原结果，不能清状态制造“未加入”。
- **恢复是新的明确授权。** 推荐由准确目标持久签署替换意图，当前有权、已达到所知水位的另一成员提交同一 Commit 的精确 Remove/Add。原 AddMember 仍按当前群主资格，原 AddDevice 仍按同账号另一有效成员资格；不开放群主代签其他账号设备、不把目标自签名当群权限。
- **只替换密码叶。** 实例、账号、设备及签名身份保持，使用全新一次性 init/leaf 材料；保留普通 never-member 限制，仅专用恢复关联可例外。原接受的当前活动端点只允许一个被接受后继；并发、取消、撤销和群变更必须事务裁决，旧包不复用、accepted 不改 closed。
- **R0、R1 和水位分别证明。** 批准者及幸存者处理实际 Commit，目标处理实际新 Welcome，各自持久后才是 R1。目标仅在专用恢复视图通过旧公开 Add，不伪造旧 MLS/R1；所知水位更高仍须补链，目录/Service 签名不证明全球新鲜性或消除 Q02 暂停。
- **离线不保证可恢复。** 幸存者按原链验证，缺链/秘密不能快进；锁定库会对迟到 Add 的 KeyPackage 校验当前期限，默认 Welcome 也可能被其他过期 LeafNode 阻断。保存全链不等于届时可应用，须分开及时补链正例和跨期限失败。当前 POC 没有纯 Update 权限动作，应等待或明确不支持，不关闭库验证、不自动移除幸存者，也不承诺全员离线时自动完成。
- **历史独立。** 用户已确认目标从新恢复状态开始，历史单独授权；本契约以恢复 epoch 作为未来通信边界，原邀请至恢复前的消息不自动补回，已合法持有的副本不删除。新 Welcome 不授旧 epoch，原消息目标/接受/设备槽及双游标不重写；缺历史槽明确隔离，不误报送达/已读。现有副本迁移仅限本群同账号不同当前设备，首次新账号未必有来源。
- **新鲜性与秘密边界保持。** 身份改变、撤销、目标已离群、独立锚未决/缺 journal/回滚、Q02 冲突均不能通过此恢复解除。旧副本即使曾加入，也需密码攻击负例验证其旧秘密不能解密恢复后 R2；不能以 HTTP 拒绝代替。保留的身份签名钥若已失陷，本流程不证明身份安全恢复。

**机制证据与限制：** 同身份精确 Remove/Add、新 Welcome、及时补链、后继通信及加密快照跨进程重载已通过；原/替换 Add 迟到和其他幸存叶过期已实际触发默认 Lifetime 拒绝。旧 SenderDataSecret 对真实新密文的直接 AEAD 失败，旧钥/旧密文及新钥/新密文正对照成功；这只是加密 SenderData 的攻击子集，未覆盖正文 ratchet/全部旧秘密攻击。该机制轮不含目标签名恢复意图、业务批准、唯一后继账本或 HTTP 恢复 API；这些能力随后在协议 22.9.11 的最小业务 POC 中实现。详细来源、失败轮和剩余矩阵以[协议 22.9.9](消息协议草案.md#2299-隔离组合-commit-与密码边界实测2026-10-14)为准，不将其外推为完整 E17 或生产安全证明。

**已固化的下一业务契约：** [协议 22.9.10](消息协议草案.md#22910-恢复动作与唯一后继契约基线2026-10-14)明确 root/current 接受引用、新恢复签名域、精确新材料与旧叶绑定、当前批准资格、唯一活动槽/唯一接受后继和原事实不可变。超时及普通错误不能释放未知候选，signed closed 必须与退役/释放原子保存；accepted 永不改 closed。期限按提交前最后重验取样判定，持久提交决定 R0 与并发胜负，不承诺 fsync 完成时刻仍未过期。目标意图至 Welcome/独立锚 Finish 的断点均列入 E01—E18；契约固化轮未实施格式、迁移和账本，也没有新增密码安全通过结论；后续最小实现及实际验收以协议 22.9.11 为准。

**后续最小业务实现：** 用户已授权本会话实施，限定闭环 `PASS_SCOPED`，见[协议22.9.11](消息协议草案.md#22911-最小恢复业务-poc2026-10-14)及[验收索引](../dist/network-relay/join-recovery/validation.json)。18个具名场景累计通过，覆盖原事实保持、两类授权、唯一后继、并发终态、真实 MLS 安装、具名故障/锚恢复、旧格式和预留容量。完整恢复/Q02/旧流/撤销矩阵、正式 SDK/Service、平台和阶段0未完成；E17仍仅保留此前 SenderData AEAD 子集。

2026-10-15 继续接入恢复原件的 Q02 观察：同一前驱的 v3/混合后继、同入口多个 accepted、accepted/closed 终态及完整检查点矛盾，随原快照和独立锚持久暂停；closed 的所知水位也不能被清除候选或旧回执重试覆盖。缺链只保存观察，不成为实际 MLS；显式恢复必须覆盖所知完整检查点，实际 R1 失败仍阻止发送。未入群公共链不授予历史秘密或发送资格，首次入群及当前 head 仍分别验证。具体行为和本机证据见[协议22.9.14](消息协议草案.md#22914-恢复原件的分叉与所知水位协调2026-10-15)；生产独立性及完整 Q02 仍未验收；随后授权的恢复证据容量验证与限制见[协议22.9.16](消息协议草案.md#22916-恢复证据容量耗尽的持久暂停2026-10-15)。容量不足以保留有效新事实时必须持久暂停，不淘汰旧证据、不假装完成 R1；匹配本机分支的 head、重试和重启均不能解除该暂停。当前没有容量暂停的原地解除入口，安全归档/迁移或独立后继重建仍须另行验证。

**已确认的产品选择：** 用户回复“采用建议：从新恢复状态开始，历史单独授权”。这不承诺补齐原邀请后的历史缺口；若另要求完整历史，须先明确新增历史授权、可用来源及不可恢复时行为。该决定不缩减一期独立历史恢复功能；随后另获授权的机制 POC 不自动授权完整业务恢复实施。

### 3.2.4 Q01 真实身份与设备目录的信任来源（2026-10-16）

**状态：契约已按用户后续授权推进到最小隔离 POC，I01—I10 的具名运行范围为 `PASS_SCOPED`，见[协议 23.5](消息协议草案.md#235-q01-身份来源最小隔离-poc-与验收2026-10-16)。以下保留信任来源契约，不代表生产身份供应方已选定。** 用户授权明确信任来源和最小验收范围；保留 3.2.1 的“先独立核验再发送、按设备身份核验”及 3.2.3 的材料耗尽等待策略，不引入账号主私钥或自动继承信任。业务身份是部署方对其业务账号的认证和稳定映射，不等于自然人实名。完整 Q01/Q02、T01—T06 与阶段 0 继续 `NOT_COMPLETE`。

#### 四种事实及其来源

| 事实 | 信任来源及验证者 | 不授予的能力 |
|---|---|---|
| 业务账号归属 | 接入方业务后端完成其身份认证，通过受信服务端入口映射稳定 IM account ID；独立业务签发器签发绑定实例、主体、用途及期限的设备登记许可，由 Service 验证 | 登录或密码重置不证明设备可信、联系人已核验，也不授予旧群和历史秘密 |
| 设备私钥持有与账号设备授权 | 设备本地产生私钥，签准确注册挑战；Service 同时检查业务许可。首设备由明确的首次登记策略授权；已有可信设备时，新设备还须该账号有效旧设备签署准确设备对象的加入批准 | PoP 只证明持钥；账号新增设备批准不等于任意群 AddDevice，群权限继续独立检查 |
| 联系人的准确设备身份 | 对方本人或已知可信联系渠道独立提供包含实例、稳定账号、设备及完整身份公钥的对象，观察者通过原 Rust 展示/确认入口逐设备核验 | 目录、Service 回执、业务签发器、旧设备批准、管理员和“接受风险”不能替联系人完成核验 |
| 目录的来源、授权连续性及所知新鲜度 | 预配置 Service 回执公钥认证响应来源；注册/批准原件验证设备进入目录的依据；版本、前驱摘要和持久水位约束已知连续性，独立可信端对照提供另一个观察来源 | Service 自签、从版本 1 连到 head 或挑战绑定响应均不证明全局最新、无遗漏或无隔离分叉 |

前序实现（以及未启用新身份来源模式的兼容路径）从 `storage.py` 的 fixture 预置访问主体，注册完成后 `key_package_storage.py` 生成 `authorization_source=synthetic-registration-poc` 的候选目录；Rust `key_package_directory.rs` 成功结果明确为 `candidate_saved_freshness_unknown`。本节固定替换这些信任前提的契约，后续显式模式的实际入口见协议 23.5；旧路径的签名挑战、哈希链和回执不因此升级为真实业务授权。

#### 可信起点与首次登记

1. 部署接入时，通过接入方受控发布/配置入口固定 `service_id`、业务签发方标识及公钥、Service 回执公钥和版本。端侧连接地址及 TLS 负责传输保护，回执钥不能仅从同一次待信目录响应自举。测试可生成本次运行的独立钥，但必须在攻击 Relay 前固定；控制器不能把任意目录响应里的钥登记成可信。换根、钥泄漏和配置分发生命周期另需契约，不支持无依据自动换根。
2. 业务后端从自己的认证上下文确定用户，不接受客户端自由指定他人的稳定账号。业务签发私钥只在独立签发器持有，Relay 和 SDK 只持验证材料；Service 不能拿客户端 bearer 或目录签名代造业务许可。最小实验用独立进程和密钥验证此边界；同机进程隔离不证明生产故障域独立或真实业务认证安全。
3. 登记许可必须绑定预分配的 device ID、完整设备身份公钥、注册挑战摘要及 nonce、实例、签发方/受众、稳定业务主体映射、唯一许可 ID、用途和有效期。设备通过已有账户认证向业务后端申请；Service 将许可、挑战、设备 PoP、账号设备授权依据及精确结果共同持久化后才返回成功。许可不得成为可重复登记其他设备的通用 token。
4. 首设备必须在 Service 权威账号记录确无既有成功登记且无历史墓碑时，才允许 `first_device`；并发首次请求至多一个成功。客户端本地空库、重装、查不到目录、超时或服务器声称“首次”都不能证明全局首次。恶意 Service 可向新观察者隐瞒过去；因此首设备业务许可也不代替联系人独立核验。
5. 已有设备时，新增设备要求新设备自身 PoP、业务许可及该账号当前有效旧设备的准确批准。批准签入目标完整对象、用途、许可/挑战关联及已知目录前驱；接受前重查批准者资格和前驱。最小 POC 暂以一个有效旧设备批准，不引入阈值恢复。全部可信设备丢失时明确返回“需账号设备恢复”，不伪装首次、不凭密码重置或管理员操作复活旧身份；恢复、换身份代际和历史授权另项设计。

#### 目录来源与发送门禁

目录必须区分“服务登记的设备”和“某群当前收件设备”。账号完整快照保留 active/revoked 及注册、加入批准的可验证引用，包含实例、账号、格式版本、单调目录版本、前驱摘要和整个快照摘要；首次/新增的授权类别不可互换。业务许可中的主体映射只按查询者授权披露必要内容，禁止公开 bearer、业务登录材料或不必要的业务个人资料。账号目录不能直接修改既有群成员集合或授予 Welcome。

目录响应绑定查询者、准确请求随机挑战和快照摘要，并由已配置的 Service 回执钥认证。客户端区分来源无效、授权无效、连续性缺口、已知回退、已知冲突、无独立对照和满足当前已知水位；同版本异摘要持久冲突，不以最新一次覆盖。完整快照在全部验证成功后整体替换，失败保留旧有效状态；撤销和冲突依据单独保留，不能被完整快照删除。缺失与空目录也必须鉴权认证，不能当作首次授权。

新观察者必须有经过独立核验的设备身份，再接收该设备签署的准确目录 head 对照；对照签名只能证明该端所见。最小 POC 复用已核验设备和原 Q02 交换/水位思想，不新增透明日志或承诺隔离攻击必然实时发现。无独立对照时仍可保存候选和开展核验，但目录不得驱动新建群、加设备、材料领取/外发或新目标集合；返回明确的“缺独立对照”。已有群是否继续通信沿原权限、Q02 和锚门禁，不因目录不可用而自行解除或额外升级权限。已知水位更高时须补完整链；有冲突则持续暂停。即使满足所有所知水位，也只描述为“满足当前已知对照”，不用“全局最新”。

独立对照可能同样过期、被隔离或与本地一起回滚；在这些假设失效时不可判定全局新鲜度。观察到真实撤销或身份变化后，相关新操作必须阻断；账号目录撤销不是密码撤销完成，仍须各群真实 Remove/新状态验证。核验、目录同步和许可续期都不能清除恢复证据容量暂停、权限未决、Q02 分叉或独立锚预约。

所有幂等查询先检查当前主体与访问权；已消费许可只能返回原请求的准确事实，不重建权限或重新签发材料。网络/验签/存储失败、签发器不可达、未知根、时钟不可信、配额满及提交未知均明确报错或保持未决，不能退回 fixture、只凭 bearer 注册或默认为已核验。正式 SDK 的这些事实归 Rust 事务；本轮契约不把原加密快照 POC 宣称为正式 SQLite 实现。

#### 最小验收范围

本轮已获实施授权的最小范围为独立实验业务签发器、原 Relay/Rust 的登记授权接入及目录对照门禁；不接真实用户资料，不实现正式 Go Service、全账号跨群撤销、账号设备恢复、UI 或四端绑定。签发器验证的是明确声明的实验业务认证入口，不能用测试自动化代替真实用户核验，也不能直接预填设备注册/信任/群权限记录作为本项通过证据。

### 3.3 新设备授权

1. 新设备登录后生成自己的身份和一次性授权请求，处于待授权状态；显示可供旧设备确认的账号、设备及指纹信息。
2. 现有可信设备经用户确认，为准确的新设备身份生成授权证明。建议 POC 挑战有效期 5 分钟、只能使用一次；到期、取消或字段改变必须重新开始。
3. Service 校验访问权限与当前版本后登记变更；其他客户端验证授权证明和状态连续性。授权成立与独立核验分别记录；首轮向新设备生成/分发 Welcome 或新增群秘密前，须按 3.2.1 完成准确设备身份核验。仅收到 Service 的“授权成功”响应不能跳过端侧验证。
4. 未来消息在状态确认、全部收件设备独立核验及其他门禁有效后发给新设备；旧历史须另走第 5 节授权迁移。并发添加/撤销冲突明确拒绝旧版本后重试，不让“最后收到的列表”覆盖可信状态。

建议普通 IM 登录凭证的续期不改变密码信任；本地身份仍在时可重新认证同一设备。单账号退出立即停任务、撤 token 并按策略清理该账号；清除本地身份后再次登录按新设备处理，不能恢复已撤销身份。关闭多设备须指定保留设备，对其余设备执行访问撤销与密码状态更新。

### 3.4 全部设备丢失或身份重置

建议一期先提供旧设备授权迁移，见第 5 节。没有可信旧设备且没有本项目支持、有效的恢复材料时，登录密码重置仅恢复账号访问：明确告知旧历史无法解密，建立新的设备身份代际，废止旧访问凭证，并向联系人暴露身份变化。

新身份不能沿用旧的“已核验”标识，不能自动继承群内密码信任或获得群密钥；原有关系可展示，重新核验/授权后才能恢复相应通信。业务资料显示名不构成身份连续性证明。管理端不能伪造旧设备授权。

## 4. 撤销、群变更与消息状态

### 4.1 三个不同的时点

| 时点 | 意义 | 可对外表达的状态 |
|---|---|---|
| R0：Service 持久化权限变更 | 撤 token、停止连接和领取、拒绝旧版本发送；非 E2EE 访问限制也在此执行 | 访问已撤销；相关密码更新可能仍在进行 |
| R1：诚实客户端验证并提交新密码状态 | 该通信范围的合法发送端已应用排除目标的状态；相关设备/群需分别处理，不能只看账号列表 | 指定通信范围已完成密码更新；无法确认的范围仍待更新 |
| R2：在 R1 状态下生成并持久化新密文 | 本项目旧钥攻击测试的边界，以绑定的状态及协议证据判定 | 只有满足 T13/T16 的实测条件，才能声称旧钥不能解密该密文 |

R0 与 R1 不合并为一个“彻底撤销成功”。旧设备已知的秘密、旧状态下生成的密文和已经解密的内容都无法收回。故意隐瞒变更的服务器可能让不同端长期停留在不同状态；在没有可信新鲜度和一致性证据前，不承诺全局即时撤销。

### 4.2 发送与在途规则

- 新发送前检查已验证的设备/群状态。已知存在撤销或状态冲突时停止生成该范围的新密文，完成新状态同步后再继续；离线端可以保留本地待发送内容，不以旧快照声称已安全发送。
- 已生成并持久化的密文、密码状态、稳定逻辑消息 ID、目标设备集合和状态版本共同保存；普通重试只重发同一条记录，不能为每次网络重试重新加密。
- R0 前已被 Service 接受的旧状态记录保留其原状态和保留期限；只有仍具当前访问权限的接收端可以继续领取，并按协议校验后解密。已撤销设备后续领取始终拒绝，已经取得的副本不能收回；接收展示须能区分历史状态，不能重新标成 R1 后生成的安全消息。
- R0 后提交的旧状态记录由正常 Service 明确拒绝。不得悄悄修改原记录的目标或密码状态；后续需要重发时，旧尝试保持终态，通过明确的重发/替代契约生成新记录。逻辑消息、尝试记录与去重关系由 Q04 锁定并测试，不能重复展示或复活已删除内容。
- 接收方无法仅凭本地时钟证明旧密文是在 R0 前生成还是由旧成员事后伪造。来自已撤销发送身份、无法证明允许接收的旧状态消息应隔离并明确显示失败，不能作为可信新消息接收；更细的历史接受边界由候选协议验证。
- 若发送端被服务器隐瞒了最新撤销，它基于旧状态生成的内容不属于 R2 保护承诺；Q02 必须评估可检测的回滚/分叉与仍存在的延迟边界，不得用“查过服务器最新列表”消除该风险。

### 4.3 群权限与密码状态

Service 验证群主/管理员/成员的业务权限；诚实客户端同时验证群成员变更的密码授权、前序状态和成员集合。建议新人仅能读加入后有权接收的消息，不能自动获赠旧群历史。移除一个用户要排除其所有设备；撤销某设备要更新该设备参与的相关单聊与群密码状态。

并发变更、旧成员再次加人、同版本冲突和非法群状态必须有显式拒绝/恢复流程；不得用重新入群或明文降级自动绕过验证。保留方可能暂时等待状态恢复，但不能把不同成员列表各自通信报为已一致。单聊与群聊的机制、前向安全和失陷后恢复条件分别验证，不能由某个库的单项能力推导整个 IM 已安全。参考 [MLS 架构 §5.3](https://www.rfc-editor.org/rfc/rfc9750.html#section-5.3) 对群状态失配及自动恢复风险的说明；这不代表本项目已选用 MLS。

## 5. 历史恢复与数据生命周期

### 5.1 建议恢复基线

| 场景 | 一期建议行为 | 关键验收 |
|---|---|---|
| 已授权新设备，旧设备可用 | 旧设备明确确认迁移对象及历史范围，经认证加密通道传输仍合法持有的历史材料 | 不经过 Service 明文；目标设备核验；迁移中撤销则终止继续导出 |
| 新群成员 | 默认从加入后的有效状态开始接收 | 不分发加入前解密密钥；不能因拥有群 ID 或附件地址绕过历史限制 |
| 同一用户的新设备 | 独立完成设备授权；可以明确授权迁移本人仍合法持有的旧历史 | 群成员的新加入与同一用户的设备迁移分别校验；不恢复已删除/已失去访问权的服务端内容 |
| 换机、重装、全部设备丢失 | 有可用可信旧设备则迁移；否则按身份重置处理并明确旧历史不可恢复 | 不以密码重置或服务器备份冒充历史恢复；关系保留不自动保留密码信任 |
| 迁移失败、重复或目标空间已有数据 | 先校验再提交；失败保留有效数据，重复不重复导入，账号/实例不匹配拒绝 | 不复制旧设备私钥和正在使用的发送计数/棘轮状态；新设备使用独立未来通信状态 |

加密备份恢复是可选候选方案，当前草案不将其视为已确认必须同时实现的第二条恢复路径。若纳入，须明确用户独立持有恢复密钥、备份包含的历史范围、完整性、反回滚边界、撤销与恢复材料泄漏处理；补充用例后才允许启用。设备授权和历史恢复能力本身仍属于一期，不能移出范围。

保留可解密的本地历史或备份会扩大秘密泄漏后的历史暴露范围；协议对已销毁消息密钥的前向安全，不等于可恢复历史在设备失陷后仍保密。恢复材料不得无验证地还原旧发送状态；如果不能证明状态新鲜度，必须重新建立未来通信状态。完全回滚本地可信状态且没有外部可信检查点时，不承诺自动检测所有回滚。

### 5.2 数值与清理规则

以下均为**建议目标/POC 参数，待产品评审与实测锁定，不是已确认生产容量或默认配置**。自动化使用可控时钟推进期限，不依赖实际等待。

| 项目 | 本轮建议值或规则 | 用途与限制 |
|---|---|---|
| 账号与设备 | 单账号目标最多 5 台设备；单客户端目标同时登录 3 个账号 | 验证上限、并存和关闭多设备；超过限制明确失败，不自动踢出任意设备 |
| 群规模 | 目标 100 个用户、每用户最多 5 台设备 | 候选按最坏 500 个设备身份评估；不是并发/吞吐保证，小组攻击用例先用 3 用户 |
| 密文与附件保留 | 建议接受后 30 天；附件到期不早于引用它的有效消息要求 | 历史接口返回明确过期状态；端侧已有副本按本地清理策略处理；不能过期后仍宣传永久可恢复 |
| 授权请求 | POC 有效期 5 分钟、一次性；旧版本请求冲突失败 | 分别测试到期边界、重放和时钟偏移；授权新鲜度不能仅靠客户端时钟 |
| 账号删除 | 立即停止新访问与待发任务；建议在线数据 24 小时内清理，备份最长 30 天自然淘汰 | 删除关联表、附件可达引用、推送绑定与映射，保留必要非秘密删除标记防复活；已交给其他成员的副本不可收回 |
| 共享数据与举报 | 账号删除不删除其他参与者自己的消息副本；举报建议结案后 30 天清理 | 对未结案和依法需留存的数据由部署方事先配置边界并告知；POC 不使用真实证据 |
| 备份恢复 | 恢复后重放账号/对象删除和权限变更记录，再开放访问；不能只还原旧数据库 | 备份保留与删除标记至少覆盖可恢复窗口；没有可靠新鲜度证明不得恢复旧权限上线 |
| 附件验证样本 | 固定 1 KiB 与 1 MiB 合成文件及衍生文件，测试截断、篡改与取消 | 只验证机制；正式格式、大小、时长、配额与压力指标在附件实现前另锁定 |

减少保留期、改变新人历史或提高规模目标都会影响验收，必须更新对应规则和用例，不得在测试失败后临时降低标准。

## 6. 协议与持久化的最低契约

本节定义行为约束；Q04 的拟议字段、实验接口源、状态及增量结果见[消息协议草案](消息协议草案.md)。`api/` 已有正在验证的 POC 定义和编码样例，尚非正式协议定稿；完整身份/群权限、模式与四端验收通过后才申请关闭对应问题。

| 契约 | 最低要求 |
|---|---|
| 上下文绑定 | 对实例、会话、安全模式、协议版本、发送者/设备、目标和密码状态建立密码可验证绑定，明确哪些字段经关联数据或协议自身认证；不同上下文密文不能串用 |
| 模式与版本 | 创建时固定安全模式；客户端和 Service 均拒绝与模式不符的调用；安全相关元数据不能仅信任服务器提示；不支持版本明确失败 |
| ID 与幂等 | 稳定逻辑消息 ID、每设备密文/尝试记录及其关系明确；同键同内容重试复用结果，同键不同内容冲突失败；整数跨四端无损 |
| 接受/送达/已读 | Service 持久化才接受；接收端校验并持久化才报告对应设备送达；用户已读独立建模；发送到自己的其他设备也应同步 |
| 原子发送 | 密码状态推进和待发送密文共同提交；失败不外发；提交后崩溃恢复同一条记录，不能回退后使用同一密码状态加密不同内容 |
| 原子接收 | 去重、有效消息、密码状态与处理进度一致提交；验证失败不改变有效密码状态、不发成功送达回执，明确记录失败/隔离结果；损坏事件不能永久卡死正常消息队列 |
| 排序与补拉 | 服务端可恢复的排序/游标与提交次序一致；并发提交、分页和推送/补拉交叠不漏消息；安全状态不依赖客户端时间排序 |
| 预发布密钥 | 候选使用 PreKey 或等效机制时，验证身份绑定、签名、领取并发、耗尽、轮换与旧密钥删除；耗尽按已评审协议失败或明确受限，不能自造降级路径 |
| 错误与资源 | 认证失败、信任变化、状态过期、冲突、无法解密和资源超限对调用方可区分；队列、重试、解析、跳过密钥缓存有界；正式名称和限额经 Q04/Q06 锁定 |

### 6.1 正式 SDK 的端侧存储与附件约束

2026-09-14 确认的方向见[端侧存储与附件管理](端侧存储与附件管理.md)，以下是未来实现与验收要求，不改写旧 POC 的加密快照、Relay SQLite 或当前四端内存包的实际能力。

2026-09-15 的[原生秘密保护实验](端侧存储与附件管理.md#15-原生秘密保护与可信配置保存)已在macOS ARM64专用文件钥匙串与SQLCipher上完成局部验证：密钥及可信配置固定、重启保持身份、锁定/缺钥暂停、篡改拒绝和完整结果精确恢复。它没有接入正式SDK，不等同于屏幕锁保护、生产Data Protection或硬件防回滚；helper的合成权威秘密仍按原实验保存，数据库/钥匙串/权威共同回滚仍可能不可检测。

四种 SDK 语言交付的 SQLite（包括 TypeScript 桌面与浏览器目标）由 Rust 持有和管理。数据库读写统一进入专用读写线程，浏览器采用等价的串行执行上下文；如何按 SDK 实例、账号或数据库分配线程/上下文仍待设计。宿主通过 SDK 查询消息与状态，查询与写入遵守相同的隔离和生命周期规则；桌面绑定、浏览器落盘后端、静态加密和平台安全存储方案仍待商议，不能将当前内存包写成已有数据库实现。随后隔离[浏览器存储验证](浏览器存储验证.md)已从普通记录扩展到真实OpenMLS状态与待发送密文共同提交、接收消息/去重/密码状态/处理游标共同提交，以及下载记录/下载游标的独立一致保存；持久未决预约使失败或中断后的密码操作保持阻断。该局部证据尚未整合到四端内存SDK；同库预约不能防全库回滚，秘密保存与安全删除尚未验证，不据此关闭Q05、T09/T10或完整阶段0。随后新增独立锚入口，以 `synthetic_local` 本机锚验证完整旧库阻断及完整候选的精确恢复，见[浏览器存储验证第 7 节](浏览器存储验证.md#7-浏览器独立锚与恢复契约)；生产独立故障域、首次信任和强制可信入口仍未完成。随后在同一本机合成信任边界内增加未决旧范围封存、独立批准的唯一新身份/存储空间与新群互通，结果和限制见[浏览器存储验证第 8 节](浏览器存储验证.md#8-浏览器未决范围安全重建)；生产恢复批准与旧历史迁移不在本项内。

全部数据库读取与写入必须经过 Rust 管理的显式事务，包含单次查询、恢复读取和迁移中的数据/结构读写；同一业务一致性单元共用事务，不能逐条 SQL 独立提交后拼成密码状态或消息结果。读事务正常结束后再交付结果，不让连接、事务或活动游标跨 FFI；失败与取消须可靠收尾，事务状态不明时暂停对应数据空间。SQLite 外的秘密保存、附件文件和独立反回滚锚仍按各自恢复协议处理；初始化与维护命令不默认获得事务外读写例外，具体限制见专项文档。

消息及其持久状态先成功提交，再派发对应数据成功事件。事件在事务结束、相关锁释放后派发，允许宿主在回调中重新调用 SDK 查询，不占用数据库执行上下文等待宿主代码。提交失败可以且必须明确回报错误，但不能伪装成消息入库、有效接收或状态更新成功。关闭、退出、账号切换和订阅取消后，迟到结果仍须核对实例、账号与生命周期归属；成功事件不能让宿主读到尚未提交的数据。此顺序不替代第 6 节的密码状态原子性，也不把本地落盘当作 Service 接受、设备送达或已读。

Rust 统一管理附件编解码、加解密、上传下载和任务生命周期，CPU 处理、网络等待与数据库执行相互隔离；不得持数据库事务或状态锁做长时间编解码、文件处理或网络传输。宿主可配置同时工作的附件数，任务队列、重试、内存和临时磁盘占用也须有界；总数与各阶段的关系、原件与衍生物计数、等待/暂停是否占位、跨账号或跨实例的配置作用域、默认数、线程池及 codec 支持范围均待商议，不能只限制网络请求却无界启动其他处理。

附件文件与 SQLite 记录不天然处于同一事务，必须验证中断后文件与记录的核对、恢复和清理；只有必要文件有效、对应状态提交成功，才能报告附件完成或可用。取消、重试和失败恢复须保留明确结果与有效数据，不重复创建消息或无依据地重新加密；取消不能冒充收回已被 Service 接受的内容。E2EE 原件、缩略图和封面均在端侧加密后上传，解密材料走 E2EE 消息；下载经完整性校验后才标为有效。临时明文须限制访问范围和生命周期，失败、取消、退出与重启清理均按账号处理，不能删除其他任务仍需使用的文件，也不承诺介质级不可恢复擦除。

## 7. 可执行 POC 验收清单

### 7.1 固定装置与证据

最小装置：独立 Rust CLI 客户端 A1/A2、B1/B2、C1；A/B/C 为不同用户，A2/B2 为各自新设备；群 G 初始含 A/B/C。另建实例 S2 中同名用户和单客户端多账号数据空间验证隔离。每个端独立持有秘密、数据库和生命周期，不靠共享内存取得对方密钥。

### 7.2 执行批次与退出

T04/T18 在执行前由 Q02 固定判定条件：对已知低版本或同一前序的可验证冲突，客户端须在生成下一条新密文前报错并暂停；对持续隔离的自洽分叉，必须说明所需的独立可信对照渠道，并验证取得冲突证据后会暂停发送。若采用的方案无法提供该检测路径，问题保持未解决并阻断阶段 0；对照前无法发现的窗口及恢复规则须事先评审，不能只登记“已知风险”就判通过。

1. **候选筛选：**先做 Q01/Q03 的资料与许可证核查、原生与浏览器最小构建，按相同标准淘汰不满足硬约束的候选。未使用的候选不加入正式依赖。
2. **身份与会话：**T01—T08、T11，取得身份授权、离线首条和错误处理证据。
3. **持久化与变更：**T09—T10、T12—T18、T20—T21，验证最易迫使架构返工的状态问题。
4. **边界与交付：**T19、T22—T26。四端构建探索可与前两批并行，最小 Release 包实际运行必须在阶段 0 内完成，不能拖到阶段 3 首次验证。

每批失败先定位模型、协议、实现或测试装置原因，保留失败证据，不删除用例换取通过。功能仍需后续完整 Service/SDK、实际平台和完整一期验收；POC Relay 的模拟故障不能替代正式数据库事务、系统推送或容量实测。

### 7.3 Q02 独立对照、隔离窗口与恢复基线（2026-10-16）

本节先固定信任契约，统一定义及最小联合矩阵见[协议第24节](消息协议草案.md#24-q02-独立对照锚保存与恢复的信任契约2026-10-16)。它补充7.2的事先判定条件，不表示完整 T04/T18、Q02 或阶段0通过。

- 独立核验设备提供有范围的观察，独立锚提供固定范围的单写承诺；两者均不能证明全局最新。最小渠道沿用逐次当面完整指纹核验和离线文件交换；自动化只记 `synthetic_local`，真实生产故障域与可信根分发仍未验证。
- 隔离窗口从最后一次有明确覆盖的独立对照，持续到下一次取得并保存有效新水位/冲突事实；可能无限长，且最后一次匹配也不证明当时全球最新。新挑战、时间戳、有效期与更大版本不能缩短这个安全边界。目录驱动的新操作和主动检查按原门禁拒绝；本轮不新增既有群定时停发策略，不把未见冲突写成已排除隐藏撤销。
- 已知回滚/缺链须满足全部所知水位、可信完整链及实际密码状态，精确当前 head 绑定新挑战后才能显式恢复。锚恢复只完成已保存的精确结果或核对当前承诺；缺结果日志不重新执行。每次仅清对应门禁，其他暂停、移除及权限候选保持。
- 已知分叉与证据容量暂停当前没有原地解除入口；健康旧范围缺日志的受限重建不能用于这些状态。未来裁决、归档迁移或隔离后继的批准与证据保全须另行验证。登录、管理员声明、删除证据、换锚或选最大版本均不是恢复依据。
- 双方共同隔离、设备与锚/配置共同回滚、根或对照端失陷是必须显式报告的不可判定/假设失效边界。暂停不追溯收回已外发密文；R0不等于R1，密码撤销仍需原定直接交付R2密文的旧秘密攻击证明。

契约固定时 Q2-01—Q2-12 均为 `NOT_EXECUTED`；用户随后授权实施，86个具名子场景按十二组取得 `PASS_SCOPED`，逐项结果与限制见[协议24.6](消息协议草案.md#246-q02-最小隔离-poc-实施与逐项验收2026-10-16)及[验收索引](../dist/network-relay/q02-isolated/validation.json)。满额有效证据现在沿用持久容量暂停；隔离后继仅能在锚保护下核验批准计划中精确成员，实际Welcome前仍拒绝发送。长期共同隔离/双重回滚负对照明确不可检测，不作为防护通过。既有历史报告只按原范围保留。矩阵全部局部通过后仍需真实独立设施、根失陷恢复、完整攻击范围及四端整合，不能仅登记不可检测风险就关闭阶段0。

## 2026-11-24 业务身份实现边界

本轮Go/PostgreSQL Alpha增加用途隔离的业务主体与短期设备凭证。业务后台对自己的已有登录负责，Service以持久映射和固定设备公钥关联约束签发；跨主体/账号/设备、错误用途和过期/撤销凭证拒绝。业务账号成功登录、目录绑定或换发访问凭证均不授权替换原密码身份，也不自动信任对端。客户端仍独立核验固定公钥，私钥不出端。

HMAC访问令牌是HTTP/WSS鉴权材料，不替代MLS；单凭证失效不能撤销成员密码能力、消除在途操作或回收旧明文。业务主体与签发密钥必须由部署方安全保管，固定两个设备的绑定不可更换；主体ID不得复用给其他组织。Service存储不可直接使用的ID/范围/期限及幂等结果，提交后才产生成功响应。当前环境变量注入、合成业务会话、macOS专用钥匙串与固定公钥核验的实际边界见[业务验收](端侧存储与附件管理.md#25-业务身份接入与-go-服务端-sdk2026-11-24)；不表示完整生产身份系统、安全审计或动态密码撤销已完成。
