# 会话协作

本文经根目录 [AGENTS.md](../AGENTS.md#会话协作) 明确纳入项目规则，仅补充 Codex 会话的拆分、续接与交接流程。用户明确要求优先；与根规则冲突时以根规则为准。这里的“会话”指 Codex 任务，不是 IM 产品会话，也不以内部子代理代替独立功能会话。

## 1. 授权与推进范围

- 自动推进授权见根规则。下一项必须是用户已授权的具体任务，或用户已确认实施顺序中的下一项；文档中列出的全部规划、Codex 临时建议或尚未明确范围的功能，不自动成为执行授权。
- 没有明确的下一项时，报告当前完成情况与待明确事项，不自行创建需求。用户后续的“只分析”“暂停”“停止”“本次不拆分”等明确要求优先。
- 本规则在当前环境可用的工具和权限范围内执行，不自行增加工具权限或后台执行能力。

## 2. 拆分边界与完成条件

- 独立功能使用独立会话。完成当前功能所需的配套修改、问题修复、相关文档和验收反馈留在原会话；不按文件数量、技术层级或对话长度机械拆分。
- 当前功能按本次明确的验收范围及根规则的[验证与完成要求](../AGENTS.md#验证与完成要求)判断完成。影响验收的未解决问题、失败或未执行事项，不得通过拆分会话标记为完成；用户明确接受剩余限制时，按已确认的边界交接。
- 新会话启动后，原功能的验收反馈仍归原会话；涉及双方正在修改的文件时，先协调修改顺序，避免并发写入。
- 每项完成后的最终回复必须说明下一步具体做什么及其验收条件；区分已启动、待启动和仅建议。下一项尚未明确或未获授权时，说明待明确事项，不把建议自动当作执行授权。

## 3. 查重与继续已有会话

- 创建前检查本项目已有会话，结合功能目标、工作范围、完成状态和代码起点判断是否重复，不只根据标题判断。
- 同一功能已有适用会话时，优先继续该会话并补充交接信息，不重复创建或重复启动相同工作；已有会话正在执行时，先核对进度及修改范围，不另开会话并行实现同一功能。
- 会话信息不完整时，如实说明检查范围，不声称已排除全部重复。新建或继续时遵循根规则的[会话标题](../AGENTS.md#会话标题)，本文不另设标题格式。

## 4. 代码接续与并发修改

- 后续功能依赖前序修改时，必须从包含这些修改的当前代码状态继续，包括必要的未提交改动和新增文件。
- 新建或复用前，核对实际工作目录、代码状态，以及适用时的分支和提交位置。不能默认从缺少前序修改的默认分支、旧目录或旧工作副本开始。
- 使用独立工作副本时，确认所需改动已经完整接续；无法确认时，不启动依赖这些改动的实现。项目尚未使用 Git 时，从当前项目目录接续，不为拆分会话擅自初始化 Git。
- 保护用户已有工作，遵守根规则的[开始工作与改动纪律](../AGENTS.md#开始工作与改动纪律)。拆分与交接不构成提交、推送、合并或改写历史的授权。
- 交接前明确文件修改归属。后续会话开始修改后，原会话不继续修改相同文件；需要处理配套反馈时，协调为顺序执行。

## 5. 交接内容

新建或继续会话时，在启动说明中提供以下信息，优先引用现有文档与验证记录，不重复建立一套报告：

1. 功能目标、已授权范围、必要依赖和验收标准。
2. 前序已完成修改、剩余限制及需要延续的决定。
3. 实际代码起点，包括工作目录、必要的未提交改动与新增文件，以及适用时的分支或提交位置。
4. 关键文件、接口契约、状态归属和现有验证入口。
5. 实际执行的验证结果，明确区分通过、失败和未执行。
6. 文件修改归属与并发限制，并要求读取、遵守适用的 `AGENTS.md`；后续功能交接同样遵循本文。

## 6. 启动确认与失败处理

- 创建请求返回后，核实新会话已创建并开始执行，再在原会话提供入口与交接摘要；继续已有会话时，同样核实已接收任务并开始执行。
- 区分“已请求创建”“创建中”“已创建”“已启动”和“需要处理问题”，不把提交创建请求写成已经启动，也不把已启动写成已经完成。
- 创建结果不确定时，先查询已有状态，避免重试造成重复会话。
- 无法创建或启动时，如实说明原因，并提供可复制的启动说明；如已有会话，同时提供其入口，不声称任务已经开始。创建工具不可用时，不用未获授权的定时任务或其他执行入口替代。
