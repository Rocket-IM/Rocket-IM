# 端侧代码生成

> 2026-09-24 名称迁移：本文的当前源码名称已统一为 `Rocket-IM`；既往运行成绩、摘要和旧包验收仍属于改名前版本，不自动适用于新包。历史 `dist/` 链接保留原始目标，旧实验状态与新协议域不能混用。本轮改名验证及复现入口见[工程名称统一](工程名称统一.md)。

更新：2026-09-15。TypeScript 以 macOS/Windows 桌面客户端为主，浏览器为次。本次最小产物选择复用现有 Rust 内存核心，另行生成 Node 宿主绑定并打包；既有 Chrome 记录仍只属于 Web 最小包。本文说明生成与交付方式，不记录本次通过结论；Windows 尚未实测，桌面应用集成仍待验收。路径均相对项目根目录。

当前已采用 Rust 导出接口和跨语言绑定生成流程。生成器负责生成调用 Rust 的代码，密码逻辑仍在 Rust 编译出的原生库或 WASM 中执行。各端公开封装和包配置由项目维护，不会全部自动生成。

本套 SDK 仍是阶段 0 的内存双设备实验，包含身份材料、建群、加解密和关闭操作。网络、业务登录、持久化、恢复同步等能力尚未整体进入 SDK。既有包验收与运行范围见[四端最小发布验证](四端最小发布验证.md)和[四端互通验证](四端互通验证.md)，本文不重复维护测试成绩。

## 1. 代码由谁维护

当前分为四层：

1. **Rust 核心。** `crypto-core` 封装密码实现，`im-sdk` 提供公共设备对象、串行访问和错误处理。
2. **Rust 桥接入口。** 三个 `bindings-*` crate 显式声明各生成器需要读取的接口，转发到 `im-sdk`。
3. **自动生成的绑定。** 负责跨语言类型转换、对象引用、函数调用、返回值、错误和资源处理。
4. **各端手写封装。** 提供适合对应语言的公开 API，处理初始化、版本检查、字节类型和资源生命周期；与预编译 Rust 产物一起打包。

| 部分 | 当前源码或配置 | 维护方式 |
|---|---|---|
| 密码核心 | [crypto-core/src/lib.rs](../src/sdk/rust/crates/crypto-core/src/lib.rs) | 手写 Rust，封装 OpenMLS |
| 公共设备对象 | [im-sdk/src/lib.rs](../src/sdk/rust/crates/im-sdk/src/lib.rs) | 手写 Rust |
| Flutter 桥接入口 | [bindings-flutter/src/api.rs](../src/sdk/rust/crates/bindings-flutter/src/api.rs) | 手写 Rust，供 FRB 读取 |
| Swift/Kotlin 桥接入口 | [bindings-uniffi/src/lib.rs](../src/sdk/rust/crates/bindings-uniffi/src/lib.rs) | 手写 Rust，使用 UniFFI 宏 |

| Flutter 公开 API | [rocket_im_stage0.dart](../src/sdk/flutter/lib/rocket_im_stage0.dart) | 手写 Dart |

## 2. Flutter：FRB 读取 Rust 桥接源码

当前固定 `flutter_rust_bridge` 和生成器版本为 **2.11.1**。生成入口是 [generate_flutter.py](../tools/platform_release/generate_flutter.py)。

脚本通过 `--rust-root` 指定 `bindings-flutter`，通过 `--rust-input crate::api` 指定接口模块。生成器读取该模块的函数、对象、参数、返回类型和桥接标记，生成 Dart 与 Rust 两侧的调用代码。

桥接源中的标记包括：

- `#[frb(opaque)]`：对象由 Rust 持有，Dart 通过桥接引用它，不直接访问内部密码状态。
- `#[frb(sync)]`：当前用于同步的 `sdk_version()`；设备操作使用当前生成配置下的异步 Dart 接口。

例如，Rust 桥接源中的加密方法为：

```rust
pub fn encrypt(&self, plaintext: Vec<u8>) -> Result<Vec<u8>, String> {
    self.inner.encrypt(plaintext).map_err(|e| e.to_string())
}
```

当前自动生成的 Dart 接口为：

```dart
Future<Uint8List> encrypt({required List<int> plaintext});
```

FRB 同时生成参数序列化、FFI 调用、对象引用及异步结果处理代码。Dart 返回 `Future` 不代表 Rust 方法本身是 `async fn`；当前 Rust 加密方法仍是同步方法，由桥接执行机制调用。

生成文件直接放入源码目录：

- [api.dart](../src/sdk/flutter/lib/src/rust/api.dart)：生成的 Dart 接口。
- [frb_generated.dart](../src/sdk/flutter/lib/src/rust/frb_generated.dart)：接口实现、序列化与调用调度。
- [frb_generated.io.dart](../src/sdk/flutter/lib/src/rust/frb_generated.io.dart)：原生 FFI 相关代码。
- [frb_generated.rs](../src/sdk/rust/crates/bindings-flutter/src/frb_generated.rs)：Rust 侧生成的接收、转换与分发代码。

外层手写 `rocket_im_stage0.dart` 负责加载预编译库、检查版本，并将对外字节参数收紧为 `Uint8List`。因此，内部生成接口的 `List<int>` 与 SDK 公开接口的 `Uint8List` 需要分开理解。

当前生成命令包含 `--no-web`，对应 Flutter iOS/Android，不代表已经支持 Flutter Web。

## 3. Swift、Kotlin：UniFFI 从编译库读取接口信息

当前固定 UniFFI 版本为 **0.31.0**。两个平台共享同一份 `bindings-uniffi` 桥接源，使用以下 Rust 宏：

- `#[derive(uniffi::Object)]`：声明跨语言使用的对象，当前对象名为 `NativeDevice`。
- `#[uniffi::export]`：声明导出函数或对象方法。
- `#[uniffi::constructor]`：声明构造方法。
- `#[derive(uniffi::Error)]`：声明跨语言错误类型。

宏在编译时提供桥接入口和接口描述信息。当前流程没有单独维护 UDL 接口文件，而是使用 Rust 宏声明和编译库中的接口元数据。

[build_rust.py](../tools/platform_release/build_rust.py) 的 `--generate-uniffi` 操作会：

1. 从当前源码构建宿主动态库及 `rocket-uniffi-bindgen` 生成器。
2. 将动态库作为 `generate --library` 的输入。
3. 分别指定 `--language swift`、`--language kotlin`。
4. 根据 [uniffi.toml](../src/sdk/rust/crates/bindings-uniffi/uniffi.toml) 中的模块名、包名和库名输出绑定。

生成器入口 [bindgen.rs](../src/sdk/rust/crates/bindings-uniffi/src/bin/bindgen.rs) 直接调用 `uniffi::uniffi_bindgen_main()`。Python 脚本负责组织构建与运行生成器，不自行编写 Swift/Kotlin 桥接逻辑。

例如，Rust 中的 `encrypt(Vec<u8>) -> Result<Vec<u8>, DeviceError>` 生成以下语言签名，省略生成器附加的修饰符：

```swift
func encrypt(plaintext: Data) throws -> Data
```

```kotlin
fun encrypt(plaintext: ByteArray): ByteArray
```

生成代码负责将字节数据转换为 FFI 参数、调用 Rust 并转换结果和错误。Swift 使用生成的 C ABI 入口；当前 Kotlin 绑定通过 JNA 调用 Rust 原生库。项目没有为这些设备方法手写一套 JNI 实现。

当前 Swift/Kotlin 设备方法均为同步调用。不会因为采用 UniFFI，就自动变成 Swift `async` 或 Kotlin `suspend`。

生成文件位于构建输出目录；以下列出默认相对路径，本轮加 `--output dist/project-rename/sdk` 后对应前缀改为该隔离目录：

- `dist/platform-release/generated/swift/`：`RocketIMStage0.swift`、`RocketIMStage0FFI.h`、`RocketIMStage0FFI.modulemap`。
- `dist/platform-release/generated/kotlin/io/rocketim/stage0/`：`rocket_stage0_uniffi.kt`。

因此，单独查看 `src/sdk/swift` 或 `src/sdk/kotlin`，主要会看到手写公开封装和包配置。打包时才将生成绑定与这些源码合并。

## 4. TypeScript 产物与 Node/Web 生成路线

TypeScript 是公开接口与类型声明的语言，不等于运行宿主。SDK 交付公开 JS 接口、TS 声明及对应运行环境所需的预编译 Rust 核心与绑定；接入方正常构建自己的应用，不需要 Rust/Cargo 或绑定生成器。macOS/Windows 桌面是主要目标。本次最小产物选用 Node 宿主与 wasm-bindgen `nodejs` 目标，复用同一 Rust 内存核心和锁定依赖，不新增 napi-rs 或另一套密码实现。

这是桌面 SDK 的 Node 运行产物验证，不锁定最终 Electron/Tauri 宿主、原生绑定或 SQLite 方案，也不将 WASM 固定为 TypeScript 的唯一交付方式。原 `src/sdk/typescript` 包继续对应 Web；新增 `src/sdk/typescript/node/` 单独维护 Node 包。在 macOS 上用 Chrome 验证 Web 包，不等于桌面 Node 验收；Node 包通过也不能推定 Windows、Electron/Tauri 或完整桌面应用通过。TypeScript 的 `NodeNext` 编译配置同样不能作为运行证据。

当前固定 wasm-bindgen 版本为 **0.2.128**。Rust 桥接源使用 `#[wasm_bindgen]` 声明导出对象和方法，也通过 `js_name` 指定 JavaScript 名称。例如：

```rust
#[wasm_bindgen(js_name = encrypt)]
pub fn encrypt(&self, plaintext: Vec<u8>) -> Result<Vec<u8>, JsError> {
    self.inner
        .encrypt(plaintext)
        .map_err(|e| JsError::new(&e.to_string()))
}
```

[build_rust.py](../tools/platform_release/build_rust.py) 先将 `bindings-wasm` 编译到 `wasm32-unknown-unknown` 目标，得到 WASM。随后用同一 wasm-bindgen 0.2.128 分别生成浏览器 `web` 或 Node `nodejs` 加载与调用代码，生成目录相互独立。

默认 Web 输出位于 `dist/platform-release/generated/wasm/`，Node 输出位于 `dist/platform-release/generated/node/`；本轮使用 `--output` 替换同一输出前缀，各自包含：

- `rocket_stage0_wasm.js`：对应宿主的 WASM 加载和调用桥接代码。
- `rocket_stage0_wasm.d.ts`：供 TypeScript 使用的接口类型声明。
- `rocket_stage0_wasm_bg.wasm`：Rust 编译并经 wasm-bindgen 处理的二进制。
- `rocket_stage0_wasm_bg.wasm.d.ts`：底层 WASM 导出的类型声明。

生成的 TypeScript 类型声明包含：

```typescript
encrypt(plaintext: Uint8Array): Uint8Array;
```

对应的生成 JS 会将输入字节放入 WASM 内存，调用 `wasm.stage0device_encrypt(...)`，检查错误，再复制返回字节并释放临时内存。密码逻辑在 WASM 中执行。

自动生成的是 JS 桥接及 `.d.ts` 等产物；Web 的 `src/sdk/typescript/src/index.ts` 和 Node 的 `src/sdk/typescript/node/src/index.ts` 是各自的手写公开封装，负责初始化、版本检查、字节复制和关闭资源。打包时用 TypeScript 5.9.3 将各自封装编译成 `index.js` 和 `index.d.ts`。这一步与 wasm-bindgen 生成绑定是两个独立步骤。

Web 初始化异步加载 WASM。Node 的公开入口为 ESM，异步导入包内独立 CommonJS 子目录；该目录保留生成器的 `nodejs` 加载器及预编译 WASM。Node 包名为 `@rocket-im/stage0-node`，版本沿用 `0.1.0-stage0.1`，与原 Web 包分别组装为 npm TGZ；安装不运行 Rust 编译或生成器，也不在加载失败时改用其他核心。

两种绑定初始化后的 `encrypt()` 等密码操作仍是同步调用。Node 最小包要求宿主通过 `node:worker_threads` 在工作线程内初始化和使用设备，宿主负责按序调用、关闭对象和退出线程；SDK 不自动创建工作线程，也没有把同步操作变成 Promise 任务池。这只是内存双设备能力，未引入数据库或正式消息引擎。

选择依据见 [wasm-bindgen 部署说明](https://wasm-bindgen.github.io/wasm-bindgen/reference/deployment.html)：`nodejs` 生成可直接 `require` 的 CommonJS 桥接。现有 `getrandom 0.2.17` 的 `js` 特性已有 [Node 随机源支持](https://docs.rs/getrandom/0.2.17/getrandom/#webassembly-support)。这两项说明可实施性；实际 Node 版本、系统和 CPU 支持仍以本项目独立包运行记录为准。

## 5. 维护者如何生成、编译和打包

### 5.1 生成入口

以下命令在项目根目录执行，只展示绑定生成相关入口；显式将本轮生成日志、目标库和绑定输出隔离到 `dist/project-rename/sdk/`，固定生成器仍复用原工具目录。维护者需要先准备项目固定的 Rust、代码生成器、依赖缓存，以及 FRB 所需的 Flutter/Dart 和 `cargo-expand`。Rust、代码生成器及部分缓存默认位于项目 `dist/`；Flutter 默认使用 `~/fvm/versions/3.41.0`，也可通过 `--flutter-sdk` 指定。这些入口不会在换机后自动安装全部工具。

```sh
# Flutter：读取 Rust API，更新 Dart 和 Rust 生成文件
python3 -B tools/platform_release/generate_flutter.py --output dist/project-rename/sdk

# Swift/Kotlin：构建当前宿主库及生成器，然后生成两种语言绑定
python3 -B tools/platform_release/build_rust.py --output dist/project-rename/sdk --generate-uniffi

# 浏览器：先编译 WASM，再生成 JS、TypeScript 声明及配套 WASM
python3 -B tools/platform_release/build_rust.py --output dist/project-rename/sdk \
  --target wasm32-unknown-unknown --generate-wasm

# Node：复用同一 Rust 导出源，生成独立的 Node 加载器与配套产物
python3 -B tools/platform_release/build_rust.py --output dist/project-rename/sdk \
  --target wasm32-unknown-unknown --generate-node
```

Flutter 生成脚本还会执行 Rust workspace 的格式化。Swift/Kotlin 生成时构建的宿主库用于提取接口信息，不能替代 iOS/Android 的目标平台库。`--generate-wasm` 和 `--generate-node` 会消费已有 WASM，因此上例同时指定目标构建，确保使用当前源码的产物；两种生成选项分别写入 Web 与 Node 目录。

### 5.2 目标库与包组装

除了生成绑定，还需准备对应平台的 Rust 二进制并组装发布包。当前实验中，Flutter、Swift/Kotlin 还需编译目标原生库；Node 与浏览器先编译 WASM，再分别生成宿主绑定。当前 iOS 包使用静态库及 XCFramework，Android 使用 `.so`，本次 Node 和原 Web 包使用 WASM。历史四端实验的目标列表、构建顺序及验证命令沿用[四端最小发布验证的复现入口](四端最小发布验证.md#复现入口)，新增 Node 包使用独立打包与消费入口，不能复用旧 Web 成绩。

| 打包脚本 | 当前组装方式 |
|---|---|
| [flutter.py](../tools/platform_release/flutter.py) | 复制手写 Dart、已生成绑定和包配置，加入 Android `.so` 与 iOS XCFramework，输出预编译包。 |
| [apple.py](../tools/platform_release/apple.py) | 合并手写 Swift 与生成 Swift，将生成的头文件、module map 和目标静态库组成 XCFramework，再打包 Swift Package。 |
| [android.py](../tools/platform_release/android.py) | 复制 Kotlin 工程，将生成代码放入临时工程的 `src/main/generated`，加入目标 `.so`，构建 AAR 并发布到本地 Maven 目录。 |
| [web.py](../tools/platform_release/web.py) | 复制手写 TS 包及生成绑定，执行 TypeScript 编译，再将 JS、类型声明、WASM 和包配置打入 npm TGZ。 |
| [node.py](../tools/platform_release/node.py) | 组装独立 Node 门面与 `nodejs` 生成绑定，保留生成目录的 CommonJS 作用域，输出含 ESM 公开接口、类型声明、预编译 WASM 和许可证材料的 npm TGZ。 |

普通接入方消费这些包，无需运行 Rust 编译器或绑定生成器，仍需对应平台的正常应用构建工具。

## 6. 为什么名称包含 stage0

`stage0` 是项目为阶段 0 实验设置的名称，不是 Rust、FFI 或生成器要求的固定格式。

Rust `Cargo.toml` 的库名、`uniffi.toml` 的模块和包名、FRB 配置及库加载代码、wasm-bindgen 的 `--out-name`、各端包清单共同决定最终名称。生成器沿用这些配置，因此 `rocket_stage0_uniffi`、`RocketIMStage0FFI` 等名字会出现在代码、二进制和发布包中。

阶段变化不要求机械改名。若以后统一正式名称，需要同步配置、公开 API、导入路径、库加载和打包脚本，再重新生成、构建并验证，不能只修改生成文件名。

## 7. 新增 Rust API 时如何维护

新增 `pub fn` 不会自动出现在四端的公开 SDK 中。当前维护顺序为：

1. 在 `crypto-core` 或 `im-sdk` 实现所需能力，明确参数、错误、状态归属及测试。
2. 在需要的平台桥接 crate 中显式开放接口；当前实验的跨端公共能力应同步三个桥接入口。本次 Node 与 Web 共享 `bindings-wasm` 导出源，但须分别生成宿主绑定、维护门面并验收；未来桌面原生桥接另行评估。
3. 运行对应生成器，检查生成文件与当前 Rust 导出接口匹配，不直接手改生成代码。
4. 根据公开 API 需要，同步四端手写封装、版本常量和包配置。
5. 编译目标 Release 库，重新组装平台包，核对生成器、运行依赖、核心与包版本。
6. 由独立消费工程安装实际包，通过公开 API 验证正常调用、参数边界、错误和资源释放；涉及互通的能力补充跨端验证。

验收需要区分生成成功、编译成功、独立包消费和目标运行。本文是源码说明，没有因编写文档而重新生成绑定、构建平台包或重跑设备测试。

## 8. 后续存储与附件边界

已确认的后续方向见[端侧存储与附件管理](端侧存储与附件管理.md)：Flutter、Swift、Kotlin、TypeScript SDK 的 SQLite 及附件任务由 Rust 统一管理，TypeScript 以 macOS/Windows 桌面为主、浏览器为次；平台仅提供环境适配并封装公开 SDK，不直接开库或执行 SQL。隔离[浏览器存储验证](浏览器存储验证.md)已从普通记录的SQLite/OPFS与Worker串行入口，扩展到真实OpenMLS状态与待发送密文、接收消息与去重/处理游标的共同提交，以及下载记录/下载游标的一致保存和持久未决预约。该POC独立生成WASM绑定并打包，运行结果详见专项记录，尚未整合到本文四端内存包，也不能替代桌面 TS 存储验收。同库预约不能防全库回滚，秘密保存与安全删除尚未验证，Q05、T09/T10及完整阶段0继续开放。随后新增独立锚入口，以 `synthetic_local` 本机锚验证完整旧库阻断及完整候选的精确恢复，见[浏览器存储验证第 7 节](浏览器存储验证.md#7-浏览器独立锚与恢复契约)；生产独立故障域、首次信任和强制可信入口仍未完成。

实现这些能力后，应从 Rust 导出公开查询、命令和通知接口，再生成所需绑定并维护各端公开封装；数据成功事件在相关事务提交成功后、事务外派发，错误仍明确返回。附件最大工作数通过公开 SDK 配置；具体接口、配置口径和默认值待确定。本节不改变前文所述内存SDK、同步函数及既有运行范围；隔离POC中的存储/通知接口不代表已经生成或整合为四端SDK接口，附件接口仍未实现。

后续所有 Rust 数据库读写都必须经显式事务，单次只读查询也不例外；事务由 Rust 核心管理，生成器不自动补足业务事务边界。公开查询在读事务正常结束后返回值，不导出连接、事务、活动游标或依赖数据库资源的惰性结果；回调触发的查询重新进入核心事务入口。
