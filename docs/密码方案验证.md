## 1. 本轮选择与原因

将 **vodozemac 0.10.0 和 OpenMLS 0.9.0** 放入两个独立、不可发布的 POC，分别验证 Olm/Megolm 机制与 MLS 成员变更机制。两者不共同接入正式 SDK，不建立可以无损切换协议的承诺。新增 OpenMLS 候选是为了比较成熟的群成员变更协议，不改变 Go Service、Rust 核心或一期范围。

暂缓 libsignal：其外部使用支持、许可证与浏览器交付路线未闭合。保留 matrix-sdk-crypto 作为备选：其设备/信任/恢复能力更完整，但需接受或准确适配 Matrix 加密事件与请求语义。四个候选根许可证均已查阅，尚未完成最终分发兼容决策。

## 2. 机制上的关键差异

- **vodozemac：**Megolm 原会话状态可推导未来状态，单纯让计数前进或让服务器停投不能完成密码撤销。探针特意保留这个反例，再验证旧接收对象拒绝新独立会话，而拿到新会话密钥的对象正常接收。这只是库 API 行为；真实方案还要让所有合法发送者换状态，并验证仅向当前授权设备安全分发。[0.10.0 机制说明](https://docs.rs/vodozemac/0.10.0/vodozemac/)
- **OpenMLS：**探针用 Remove/Commit 推进成员集合和 epoch，保留成员处理新状态，被移除者保留旧活动状态并直接拿到新密文。本轮检查公开 API 的 `WrongEpoch` 拒绝；没有绕过 API 检查用裸旧秘密攻击密文，不能据此完成 T16。[版本化官方示例](https://github.com/openmls/openmls/blob/openmls-v0.9.0/openmls/tests/book_code.rs)
- **身份仍要自己解决：**OpenMLS BasicCredential 和测试中直接传递的公钥/群密钥都不证明业务用户真实身份。把双方设备放进 MLS 群来实现单聊，是应用层映射方案，尚待验证；多设备时不能简化成永远只有两个成员。[身份边界](https://book.openmls.tech/user_manual/identity.html)
- **持久化不能省略：**pickle 往返或内存 provider 不证明崩溃一致性。OpenMLS 0.9.0 还对存储格式和迁移有约束，不能直接套用旧版非自描述格式；签名密钥、KeyPackage 等需要单独处理。[迁移说明](https://book.openmls.tech/user_manual/migration.html)
- **分叉没有自动解决：**库的恢复功能不提供全局最新目录证明。仍按 Q02/T04/T18 验证独立可信对照、离线窗口和停止发送条件。[OpenMLS 分叉恢复边界](https://book.openmls.tech/user_manual/fork-resolution.html)

以下命令从项目根目录执行，需要维护者提供 `poc/rust-toolchain.toml` 指定的 Rust 和 wasm-bindgen CLI 0.2.128；Python 需要 3.11 或更高。临时工具链目录可能被系统清理，仓库内锁文件及源码保留。

```sh
python3 tools/verify_crypto_probes.py native
python3 tools/verify_crypto_probes.py wasm
python3 tools/collect_crypto_licenses.py
python3 tools/verify_crypto_probes.py serve
```

生成 WASM 后，用真实浏览器打开 `http://127.0.0.1:8765`，查看两项结果、构建 ID 和浏览器版本。`serve` 无需 Cargo、不重建，须保持进程运行，Ctrl+C 停止；不能双击 HTML 直接运行。HTTP 只服务生成产物目录，不暴露仓库、凭证或工具缓存。原生命令运行格式检查、Clippy、Release 测试及 CLI；WASM 命令只构建/生成绑定，不自动宣称浏览器运行通过。可用 `--candidate vodozemac` 或 `--candidate openmls` 单独诊断。

临时日志位于 `dist/crypto-probes/logs/`；产物在 `dist/crypto-probes/target/` 和 `dist/crypto-probes/browser/`。这些目录不纳入源码；最终结论在本文记录，可由上述入口重现。

## 5. 依赖许可证核查边界

首轮锁定依赖的 native/WASM 可达图合计 **182 个不同的 crate 版本**，均有许可证声明。vodozemac 的 native/WASM 图分别为 78/89 个，OpenMLS 为 148/159 个；后续实验的当前数量见第 7 节。这些是 Cargo metadata 图统计，不是二进制中代码量或正式 SDK 的最终依赖数量。

OpenMLS 图中 `hpke-rs`、`hpke-rs-crypto`、`hpke-rs-libcrux`、`hpke-rs-rust-crypto` 0.7.0 声明 MPL-2.0。因此不能把 OpenMLS 本体 MIT 写成全部依赖都只有 MIT/Apache。部分包未附带根目录许可证文件，需要回到对应源码版本补足分发材料；现有表保留空摘要，不自动当成没有义务。

**Q03 仅完成资料与声明采集，未完成兼容批准。** 项目 LICENSE 尚未确定；正式采用前须逐项确认实际启用组件、修改情况、源码/二进制分发义务、NOTICE 和许可证文本，决定最终项目许可证及发布方式。未构建的 libsignal/matrix-sdk-crypto 未生成传递依赖清单。

## 6. 首轮结论与阶段状态

首轮收敛了进入实验的候选并完成最小原生/WASM 运行验证。依据成员变更模型，选择优先推进 OpenMLS 身份授权、状态持久化及旧钥验证；后续实际进度和阻断见第 7 节。vodozemac 保留作独立密码层对照。这是本项目的阶段性判断，不是最终协议选型。

后续按 Q01/Q02/Q04/Q05 建立真实进程隔离的 Rust CLI 与不可信 Relay，补齐可信身份、密钥安全分发、攻击装置和事务恢复；再完成四端最小 Release 包独立消费。任何候选遇到核心安全、平台或许可证阻断都重新评估，不能为保留候选缩减一期验收。

## 7. OpenMLS 授权与恢复实验

状态：合成授权、快照和进程恢复的局部验证已通过；旧钥底层测试受平台访问限制，未执行。本次继续第 6 节的实验，范围限定为合成身份、Unix 本机单 writer、真实独立进程和文件快照；不创建第二套正式后端或 SDK。

### 数据、接口与提交边界

- `openmls-state-lab` 每次从标准输入读取一个限长 JSON 请求，在独立设备目录加载状态，执行后退出。设备与账号上下文、私钥、OpenMLS 全量存储、群标识、可信公钥、已消费授权 nonce、outbox 和 inbox 的唯一所有者是该设备。
- 首个联系人/设备公钥由独立可信的合成测试调度器提供。调用 OpenMLS 验证真实 KeyPackage，再核对业务上下文和固定公钥；不把 Relay 给出的公钥或普通 token 视为信任依据。授权声明使用已有设备 Ed25519 签名，绑定服务、账号、新设备、公钥、KeyPackage 摘要、版本、随机 nonce 和有效期。
- 全部端侧状态写入同一个 AES-256-GCM 加密快照，采用随机 nonce、版本头和上下文认证。独占设备文件锁后，临时文件同步、原子替换、目录同步；提交成功后才向外返回密文或接收确认。无法判断目录同步持久性时明确失败，不虚报旧文件仍在。
- 发送重试按消息 ID 读取已保存的密文，异内容复用同 ID 则报错；接收去重记录和密码状态共同提交。控制操作的 Commit/Welcome 也保存结果以应对提交后响应丢失。
- `poc_relay.py` 是测试装置中的独立 stdio 信箱进程，只接收公开路由与不透明字节，不读取客户端目录。它不提供 HTTP/WSS、生产鉴权或数据库事务；同一主机/UID 的进程分开不等于操作系统级敌对隔离。

每个设备目录仅支持一个实验群；同账号新设备需先通过授权，跨账号联系人使用可信 fixture 公钥。当前 Commit 接收不允许 Add/Re-add，避免旧公钥自动恢复成员身份；真实新增成员流程与群权限另行实现。信箱只覆盖串行调度，不作为并发提交或崩溃持久化的服务端证据。
