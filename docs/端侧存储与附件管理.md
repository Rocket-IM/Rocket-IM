## 1. 本次确认与范围

- 服务端继续使用 PostgreSQL，由 Go Service 管理消息持久化、投递及访问权限。
- Flutter、Swift、Kotlin 和 TypeScript 的目标平台统一以 **Rust 管理 SQLite** 为目标。TypeScript 的桌面与浏览器运行环境分别适配和验证，宿主均通过公开 SDK 访问。
- 发送、接收及消息持久状态变化先成功入库，再通过相应回调或事件通知宿主。宿主后续通过公开 SDK 查询或提交业务写操作，数据库实际读写统一进入 Rust 管理的读写线程。
- **Rust 的所有数据库读取和写入都必须在显式事务中进行，包括单次只读查询。**事务由 Rust 统一开启、提交或回滚，宿主不持有连接或事务句柄。
- 附件编解码、E2EE 加解密、上传、下载及任务状态由 Rust 实现和管理；宿主可以设置最大附件工作数。
- 上述架构确认时只修改文档，后续隔离实现以专项验证记录为准。第一期 21 项、第二期 12 项及阶段 0 出口要求不变，不据此启动正式业务实现或修改现有实验包。

本文集中维护存储与附件管理边界；[交付物与技术栈](交付物与技术栈.md)概括选型与职责，[开发路线与检查清单](开发路线与检查清单.md)及[功能分期与验收](功能分期与验收.md)记录实施与验收。密码原子性、身份和恢复限制继续遵循[安全与身份模型](安全与身份模型.md)和[消息协议草案](消息协议草案.md)。

## 2. 数据存在哪里、由谁持有

| 数据 | 所有者与位置 | 平台或宿主边界 |
|---|---|---|
| 服务端消息、收件与投递记录 | Go Service 管理 PostgreSQL；E2EE 正文仅保存密文 | 客户端和接入方业务后台通过公开 API 访问，不直连 IM 表 |
| 端侧消息、发送记录、去重、游标、密码状态及附件任务记录 | Rust SDK 管理本地 SQLite，按服务实例与账号隔离 | 宿主通过公开 SDK 查询和业务命令访问，不自行打开同一数据库或写入内部表 |
| 本地附件、派生文件与临时文件 | Rust 管理文件生命周期及 SQLite 中的关联记录；平台提供必要文件访问能力 | 不因采用 SQLite 就要求把全部大文件装入数据库；文件或 BLOB 的具体组织、路径与配额待设计 |
| 服务端附件 | 沿用先提供持久卷实现、再扩展 S3 兼容存储的规划 | Rust 管理端侧传输；Service 继续负责鉴权、配额和服务端存储，不托管用户解密私钥 |
| 端侧秘密或数据库包装密钥 | 由端侧持有，接入适用的平台安全能力 | Keychain/Keystore 等通过薄适配使用；数据库加密、macOS/Windows 桌面与浏览器秘密保存方案分别验证 |

“SQLite 由 Rust 实现管理”指 Rust 负责连接、表结构、迁移、事务、查询、写入及生命周期，使用成熟 SQLite 实现，不自行重写数据库引擎。正式 SDK 的 Rust 绑定、版本、TypeScript 桌面交付及浏览器构建方式尚未锁定；隔离 POC 使用的精确候选版本见[浏览器存储验证](浏览器存储验证.md)。

平台适配可以提供应用数据位置、文件句柄、安全存储、执行环境和必要系统能力，但不拥有另一套消息数据库或附件业务任务引擎。UI 可以保留展示状态；消息持久状态以 Rust SDK 已提交的数据为准。新增读写需求优先扩展公开 SDK，不要求宿主拼接 SQL。

## 3. 统一读写线程与回调

### 3.1 数据库执行边界

所有 SQLite 查询、写入和迁移都经过 Rust 的统一调度入口，并在数据库所属的读写线程串行执行。原生端的物理线程数量、各服务实例/账号是否共享线程，以及连接与文件如何划分，留待设计；TypeScript 桌面宿主与 Rust 的执行边界也须随绑定路线明确，不能由各平台包装层各建一套数据库读写路径。

浏览器需使用经过验证的 Worker 或等价串行执行上下文实现相同的数据库所有权，不能直接套用原生线程和文件系统。隔离POC已通过Worker串行调用Rust管理SQLite/OPFS；具体实测范围见[浏览器存储验证](浏览器存储验证.md)，正式SDK整合与完整平台验收仍未完成。

宿主通过公开 SDK 异步查询或提交业务写命令；查询返回一致的已提交结果。更新 UI 的回调与结果由平台包装按对应 UI 执行环境交付或明确其切换责任，数据库线程不是 UI 线程。

附件编解码、大文件处理和上传下载由 Rust 的其他受控执行资源承担。不得持 SQLite 事务、数据库执行占用或核心状态锁等待网络、执行耗时编解码或调用宿主代码。

### 3.2 所有数据库读写必须进入事务

核心内部访问与宿主经 SDK 发起的访问使用同一规则：单条查询、列表分页、计数、恢复时读取状态、增删改、附件任务记录，以及迁移中的数据和结构读写，都必须通过 Rust 管理的显式事务入口。不能因为只有一条 SQL、只读取数据或已在统一线程中执行就绕过事务。

SQLite 本身会为普通数据库访问自动开启隐式事务；本项目要求进一步由 Rust 明确控制事务边界，不能用“SQLite 自动处理”代替这一工程约束。读事务用于取得一致快照，写事务可包含关联读取和修改；不要求只读查询取得写事务。具体事务模式与数据库绑定待实现时确定，参见 [SQLite 事务说明](https://www.sqlite.org/lang_transaction.html)。

一个需要保持一致的业务单元使用同一事务及同一事务句柄：例如同次查询的会话列表与配套计数，或一次消息提交的消息、去重、密码状态与相应游标。不能逐条 SQL 各自提交后声称已满足业务原子性。迁移中的结构/数据变更与对应版本记录也须在同一事务提交；内部函数复用外层事务，不自行提前提交。需要局部回退时是否采用保存点另行设计，不能重复开启嵌套的 `BEGIN` 事务。

读事务完成查询、将结果转换为不依赖数据库句柄的值并正常结束后，才向宿主交付成功结果；写事务只有提交成功才交付对应成功结果和状态事件。不跨 FFI 传递连接、事务、活动查询游标或依赖这些资源的惰性结果，也不为等待下一次 UI 分页请求而保持读事务。不同次分页或回调后的查询可能观察到更新的已提交状态，跨请求的一致性仍由 SDK 的分页/版本契约定义。

读取、写入、提交或取消过程中出现失败，Rust 必须明确结束或恢复事务、释放资源并报告结果；不能假设任一 SQL 错误都已自动回滚全部操作。事务状态不明或无法可靠收尾时，应暂停对应数据空间的后续工作并明确报错，不能把连接交回队列继续使用。提交结果未确认时不得发成功通知或盲目重放密码状态推进。

业务拒绝与数据库执行失败分开处理：例如发现可信状态冲突时，协议要求先在事务中保存暂停状态，再返回发送拒绝，不能把“返回业务错误”统一实现为回滚掉必须保留的安全状态。若暂停状态本身保存失败，也须明确报错并保持阻止发送。

事务保持短小，只覆盖需要一致的数据访问。耗时计算所需数据可在读事务中取得后退出，再执行处理；提交处理结果时进入新的写事务，重新核验依赖版本、账号及任务状态，不能按过期快照覆盖新状态。密码状态、待发送密文和接收记录仍遵守第 4 节的共同提交要求，分离耗时处理不构成拆散原子提交的许可。

该规则不把附件文件、网络请求、平台安全存储或独立反回滚锚变成 SQLite 事务的一部分；这些边界仍需各自的恢复协议。连接初始化和维护命令也必须核对 SQLite 的事务限制：例如 `VACUUM` 不能放在已开启的事务内，见 [SQLite VACUUM 说明](https://www.sqlite.org/lang_vacuum.html)。本次不引入此类命令或开放事务外数据读写例外；若后续需要，须先明确适用边界与恢复方式，不能用“所有 SQL 一律包 BEGIN”代替设计。

### 3.3 提交与通知边界

1. Rust 校验业务输入，在显式写事务中完成相关读取与状态变更，并提交 SQLite。
2. 提交成功，退出事务及相关临界区。
3. 再向宿主派发对应数据成功事件。回调可以触发新的 SDK 查询或写命令，这些操作重新进入统一读写入口。

不得让数据库线程同步等待宿主回调完成。必须验证回调内立即查询、提交其他命令或取消订阅时不会重入死锁。

“先入库再回调”约束的是数据成功事件；初始化失败、校验拒绝、磁盘写入失败等仍通过明确错误通道回报，不能因没有成功入库而静默。需要持久化的失败状态应在保存成功后通知；保存失败本身也必须可观察。

回调是已提交状态变化的通知，不是消息的唯一副本或唯一恢复依据。通知应能定位服务实例、账号及变化对象；是否携带摘要、变化版本、合并事件及具体字段仍待商议，不能把全量数据库状态或内部密码类型穿过绑定边界。

进程退出、订阅取消或 UI 生命周期变化可能造成通知未被消费。初始化查询与订阅衔接必须避免遗漏窗口；重订阅后应能通过 SDK 查询或变化补取恢复已提交状态。具体采用快照版本、变化序号还是其他方式，实施前确定。重复和迟到通知不得重复创建消息，也不得跨账号或跨引擎生命周期生效。

## 4. 消息先入库的具体含义

### 4.1 发送

宿主提交发送动作后，由 Rust 创建本地消息或发送意图并持久化，再通知“本地已保存”的对应状态。附件尚未准备好或密文尚未就绪时，记录必须保持明确的待处理状态，不能据此报告已发送。

真正外发之前，待发送密文、原始信封、稳定消息/尝试 ID、目标集合及对应密码状态必须一致持久化。普通重试复用仍有效的已保存尝试；需要替代尝试时继续遵循协议的显式替代规则。

若加密库内存状态已推进而数据库提交失败，不能仅回滚 SQL 后继续使用不一致的密码状态。恢复或暂停须同时满足既有密码一致性和反回滚约束，具体持久化适配需专项验证。

Service 只有在 PostgreSQL 成功提交后才能确认接受。Rust 收到并核验接受结果后，先保存本地状态变更，再通知宿主。本地入库、Service 接受、设备送达和已读保持独立含义。

### 4.2 接收

收到网络数据时先校验大小、范围和基本结构；“先入库”不代表无条件保存任意外部输入。

沿用协议对下载与处理的区分：原始有效事件和下载进度可先共同保存为待处理；完成密码身份、上下文和内容验证后，业务消息、去重、密码状态、处理结果及处理进度一致提交。缺依赖、失败隔离和有效消息必须分别记录和通知，不把未解密或未验证记录当作正常消息。

仅对已经验证有效且完成原子接收提交的业务消息，由 Rust 管理设备送达回执和重试，不等待 UI 消费回调或再次查库。仅下载、等待依赖、失败隔离或不可用占位的保存不产生成功送达回执。已读仍来自实际阅读后提交的业务命令，不能由下载、解密或回调自动推定。双游标与已提交状态保持一致，不能为了统一读写入口而合并其语义。

附件消息本身有效接收与附件文件下载、解码完成分别建模。附件暂未下载不应被伪装成消息丢失，也不能因为消息已入库就把附件标记为本地可用。

## 5. 附件由 Rust 管理

### 5.1 任务与处理职责

Rust 负责附件任务建立、编解码调度、加解密、上传下载、重试、取消、恢复和清理，并将需要恢复的任务状态及消息关联保存到 SQLite。宿主负责文件选择与授权、提交操作、配置并发和展示进度。

媒体编码/解码与 E2EE 加密/解密是不同处理步骤。具体支持格式、压缩或转码要求、缩略图/封面处理范围、codec 库和平台硬件能力需另行商议。Rust 统一实现和管理流程，不等于已经证明所有格式均能由纯 Rust 库在四端处理；确需系统能力时通过薄适配调用，平台不另建业务调度与重试队列。

### 5.2 发送与接收

发送附件时，先保存消息发送意图和任务关联；Rust 管理输入材料与处理过程。E2EE 原件及衍生文件加密后才上传，解密材料通过 E2EE 消息传递。上传结果得到确认、必要对象引用与校验材料准备完成后，才准备并持久化可外发的消息尝试。上传完成不等于消息被 Service 接受。

输入材料的读取权限和生命周期必须可控，不能假设宿主提供的临时路径在重启后仍有效。是否需要复制输入、流式处理以及输入失效后的恢复行为，在文件接口设计时确定。

接收附件时，Rust 校验当前访问条件，管理下载、完整性验证、解密和所需解码。未通过验证的内容不能作为有效文件交给正常展示流程；解密或格式失败须明确区分。下载是否自动开始、按需下载的触发方式及播放适配留待 API 设计，不因任务归 Rust 就默认自动下载全部历史附件。

### 5.3 文件与数据库的一致性

SQLite 事务不会天然覆盖附件文件或远端上传结果。必须定义暂存文件、有效文件、数据库关联和远端对象在中断后的核对、继续或清理规则。

只有必要文件已有效保存且对应数据库记录提交成功后，才能通知附件“本地可用”。重启后不能仅凭进度百分比恢复为完成；应核对已保存状态、文件及必要服务端结果，再继续、重试或明确失败。

重试应复用仍有效的处理产物和操作标识，不无条件重复编码、加密、上传或创建消息。取消请求不等于立即消灭所有在途结果；必须定义停止调度、处理在途操作、释放资源及清理后的完成边界。已上传对象和已接受消息仍按各自清理与消息协议处理。

临时明文、失败文件、孤儿对象和过期缓存都须有范围、配额和清理规则。退出账号与删除历史数据是不同动作；旧任务、文件句柄及迟到回调不得写入其他账号或新的引擎生命周期。不承诺已导出副本可收回或底层介质上的全部秘密可可靠擦除。

## 6. 最大附件工作数

公开 SDK 需支持宿主设置最大附件工作数。限制应覆盖实际执行的编码、解码、上传和下载，不能只限制网络请求而无限启动其他处理阶段，也不能让缩略图等子任务绕过资源控制。

实施前必须商议并固定以下口径，本文不预设接口名、默认数值或线程池数量：

- **计数单位：**一份附件贯穿多阶段占一个名额，还是每个活动处理阶段计数；原件与衍生任务如何计数。
- **限额关系：**采用统一总上限还是分项设置，若同时提供，如何保证分项不能绕过总限制。
- **作用域：**按宿主 SDK 实例、服务实例还是账号生效，多账号和多个实例如何共享资源预算。
- **占用与调整：**等待网络、暂停、等待重试是否占名额；运行中调低上限如何处理已有任务。
- **配置边界：**默认值、允许范围、非法值、排队容量、背压、公平性、优先级及资源峰值。

需要区分“排队数量”“实际活动工作数”和“数据库线程数”。并发配置用于控制附件负载，不赋予宿主直接管理 SQLite 线程的权限。活动任务、待运行队列、单任务子工作、内存和临时文件均需有界，并提供明确的超限结果。

需要恢复的任务状态变更在提交后通知；瞬时传输进度是否合并、多久持久化及回调频率待设计。瞬时进度不得替代数据库中的最终成功状态。

## 7. 浏览器统一目标与验证条件

本节针对 TypeScript 的次要浏览器目标，保留浏览器特有的验收条件。macOS/Windows 桌面需要分别验证 Rust 运行产物加载、执行与进程生命周期、数据位置、安全能力及多窗口访问；不要求先完成浏览器 OPFS 路线，也不将浏览器成功结果视为桌面通过。

TypeScript 浏览器端同样使用 Rust 管理 SQLite，不能继续把 IndexedDB 当作与 SQLite 并列的另一套消息业务数据库。若评估某种浏览器存储能力，只作为 SQLite 底层持久化适配的候选；隔离POC已采用SQLite/OPFS，正式SDK的选定方案与支持矩阵仍须按实测结果评审。

浏览器需单独验证 SQLite/WASM 构建、持久化介质、Worker/执行环境、事务恢复、绑定和打包方式，以及多标签页同时访问同一账号数据的所有权。不得让多个不协调的写者破坏数据库或密码状态。

必须覆盖刷新、关闭或重启 Worker、标签页异常退出、空间不足、存储不可用及用户清理站点数据。失败须明确回报，数据丢失按既定恢复与新身份规则处理，不能静默回退内存模式后声称已持久保存。SQLite/WASM 不提供对恶意宿主脚本的隔离，也不等于已经具备原生安全存储能力。

## 9. 原生普通记录事务与重启实验

### 9.1 范围与实现

2026-09-15 用户继续授权本项，代码位于 `poc/native-storage/`，维护者入口为 `tools/native_storage/verify.py`，独立输出为 `dist/native-storage/`。只保存本轮生成的普通合成记录，现有 Rust 内存核心、四种语言包、消费工程、浏览器POC与历史运行报告均不变。本项没有 TypeScript 原生绑定、真实密码状态或正式消息业务。

一个实验实例独占一条 Rust 数据库线程和连接，命令队列上限32；CLI调用线程通过值类型请求/响应等待结果，不直接执行业务SQL。该同步实验API会阻塞调用方，不能直接作为UI线程上的正式异步SDK。数据库文件固定服务实例与账号，错配拒绝打开，空路径和 `:memory:` 被拒绝，不降级临时或内存存储。测试专用的第二读取进程也是Rust连接，仅用于产生真实提交竞争。

`database.rs` 负责生命周期与普通写入，`schema.rs` 负责固定格式和一致快照，`transaction.rs` 统一显式事务和收尾；初始化、版本读取、迁移、PRAGMA检查、单次查询和恢复读取均在事务中。一次写入共同保存记录、记录更新修订号和数据空间修订号，检查预期版本，内部函数复用外层事务。v1到v2的列、已有数据和版本号同事务迁移，失败保留旧结构及数据。修订号以规范十进制字符串传递并验证u64范围，不转JS number；记录上限128、键与范围标识上限128字节、单值上限4096字节。

每次查询/写入只有在事务正常结束后才能返回成功。COMMIT失败时保留事务所有权，检查是否已被SQLite自动回滚，再显式收尾；提交或收尾未确认使本实例暂停，不继续复用。普通SQL失败在确认回滚后可继续。这里关闭重开恢复的是非秘密普通记录，不能直接照搬为加密状态恢复策略。

订阅使用独立有界接收端，事件含服务、账号和已提交修订号。数据库线程只在提交结束后非阻塞入队，不调用或等待宿主回调；注册与基线查询作为同一串行命令完成。事件队列上限16，满后明确返回 `lagged` 并断开该订阅，重新订阅取得当前快照；取消或替换后，调用方须丢弃旧接收端的排队事件。`delivered` 仅表示本条成功命令已入队，不继承到失败或只读响应，不等于UI已消费。当前实验不承诺事件恰好一次、跨进程订阅延续或正式SDK的完整取消语义。

## 10. 原生密码状态与待发送密文共同提交

### 10.1 范围与状态归属

2026-09-15 用户继续授权本项。在同一 `poc/native-storage/` 中新增 `src/crypto/` 与独立 `native_crypto` 命令行装置，只使用当轮新生成的合成身份。原普通记录库仍保持自己的格式；密码实验使用新文件和固定四表格式 `Rockets-IM/native-crypto/sqlite/v1`。已有文件缺表、格式损坏或服务/账号/设备错配均明确拒绝，不补表、不清除预约，也不静默创建新身份。

每个实例由一条专用Rust数据库线程独占SQLite连接，内部命令队列上限8。初始化、结构检查、公开状态读取、provider读取、预约及最终写入均使用显式短事务。OpenMLS创建、恢复、建群、加密和候选序列化在调用线程执行，数据库线程不执行密码计算或等待宿主回调。此同步实验接口会阻塞调用方，尚不是可直接交给UI的异步SDK。

一次密码操作分三步：

1. 写事务先检查持久未决预约，再检查请求缓存、幂等冲突和容量；保存请求号、操作及输入摘要、旧修订号和旧provider摘要，并确认预约COMMIT。该事务不读取私密provider BLOB，也不创建或恢复密码引擎。
2. 独立短读事务确认同一预约和旧状态，再读取并核对实际provider字节摘要。事务结束后，调用线程只执行一次密码操作，形成临时候选；读取、计算或序列化失败均保留预约。
3. 最终写事务再次核对预约及旧状态，一次提交provider、公开身份/群状态、密文outbox、请求结果、修订号和加密计数，并删除预约。只有COMMIT成功收尾才交付结果及带服务/账号/设备/修订号的成功事件。

这里的成功事件只是实验命令响应中的提交后事件记录，没有实现新的正式订阅接口。内存Bob进程只验证返回密文确实可解密，不提供接收落盘、已读或Service投递证明。外层路由、成员身份和消息标识纳入认证数据及加密正文校验。

同一请求号及输入返回原结果；同一发送attempt、消息号及正文换请求号也只返回已有密文。缓存不产生新事件，不创建/恢复provider或调用加密。请求号、attempt或消息号冲突在密码调用前拒绝。有未决预约时，合法的初始化、建群、同请求重试、新请求和旧成功缓存全部拒绝；重开不能解除。预约COMMIT被明确拒绝且已自动回滚时，当前实例暂停，重开确认没有预约后才允许重新开始。实验没有解锁、清空预约或旧状态恢复入口。

请求/attempt/消息与范围标识限制128字节，正文1—4096字节，结果及outbox各限制128条，provider限制2MiB/4096条，协议字节限制64KiB；修订号和计数均为规范u64十进制字符串。初始化命令同其他命令严格拒绝未知字段。

### 11.1 实验契约与格式变化

| 输入 | 处理与成功交付 |
|---|---|
| 新连续序号、新消息 | 先提交预约，再恢复并调用OpenMLS接收一次；最终共同保存provider、唯一消息、投递记录、结果、解密计数、修订号和处理游标，并清除预约。COMMIT后才返回正文和新消息事件 |
| 已保存的同一序号与同一完整输入 | 同请求号或新请求号均返回原结果，`cached=true`；不预约、不恢复/解密、不修改状态、不再次派发事件 |

| 序号已有其他输入 | `receive_sequence_conflict`；同请求号换输入仍先返回 `crypto_request_conflict` |
| 同一消息标识对应不同完整密文 | `receive_message_conflict`，不能按消息号静默忽略篡改或冲突 |

## 13. 原生完整数据库回滚与独立锚

### 13.1 绑定、承诺与可信边界

继续扩展同一原生隔离POC，新增 `native_anchored` 专用入口，复用已有OpenMLS实验的签名锚helper。锚由独立进程保存，实验配置及其签名密钥放在设备备份之外；这仍是本机受控的 `synthetic_local`，不是生产独立故障域或硬件防回滚。普通v3入口与旧报告保留，现有五份SDK归档、SDK源码、浏览器实验和正式Service均不改动。

首次绑定必须显式执行 `--bind`：对已初始化、无密码未决预约且身份范围匹配的v3实验库，在一个写事务加入 `anchor_control`、更新格式及 `user_version=4`，返回完整head，随后由合成夹具初始化独立锚。日常入口只接受v4与同一外置配置，不能自动创建锚、补库、升级、替换身份或退回普通入口。v4库被普通入口打开，或先打开的普通句柄遇到另一句柄完成绑定，都必须拒绝后续业务访问。固定可信入口遇到绑定前v3备份也拒绝；原普通入口仍能打开原v3实验库，因此首次信任和宿主强制入口保护仍是外部前提，不能声称全部入口均已防降级。

head承诺在Rust显式事务内计算，使用带类型和长度的SHA-256编码，涵盖精确业务DDL、版本和七张业务表的全部列与行：实际provider字节、密码预约、结果、待发送密文、已接收消息/正文、投递去重、原始下载记录及两个游标。不能只比较修订号或库内provider摘要。单行限制4MiB、完整编码限制64MiB；业务原有更小容量继续生效。锚控制表单独签名以避免自引用。head表示逻辑内容，不是SQLite物理页或整个文件的原始SHA；完整已关闭文件副本的摘要另由夹具记录。

协议复用Ed25519签名、随机挑战、请求摘要、范围绑定和 `expected_revision` 比较更新。范围含服务、账号、设备、密码身份和独立存储标识；响应必须匹配请求、动作与锚公钥。签名门和恢复日志另用本地专用签名域，绑定完整配置指纹。helper调用有5秒时限和输出上限，失败回收进程，不自动重试。秘密配置不进入协议请求或控制日志。

### 13.2 操作顺序与有限恢复

| 阶段 | 必须满足的条件 |
|---|---|
| 本地门 | 先在短事务保存签名门，绑定原始head、请求摘要和新事务标识；旧门、密码预约或恢复日志未解决时不进入业务 |
| 锚预约 | 在数据库事务外核验Inspect，随后Reserve比较head及锚修订号；确认并持久化本次预约后才允许恢复OpenMLS、运行密码计算或交付缓存 |
| 本地候选 | 沿用原密码预约与最终提交链；每个读写事务复核锚门和完整base。中间密码预约只在精确核对后计算“预约表为空”的base投影，不真实清除记录 |
| 最终业务事务 | 密码状态、消息/密文、结果或原始下载与游标提交时，同时保存签名恢复日志，含精确门、目标head和完整结果；缓存命中也须保存同事务日志 |
| 完成与交付 | 在事务外Finish同一预约，核验目标head、修订号和无未决状态；短事务只清除匹配的完整日志/门，之后才向命令调用方交付结果和成功事件 |
| 显式recover | 只使用已提交且签名有效的完整日志，要求当前完整head、门、目标完全一致；Finish同一事务或确认其幂等完成后清门。零密码恢复/计算，不再次派发消息事件 |

计算完整head会读取provider字节，但不恢复或调用OpenMLS；不能将本项描述为“所有provider字节读取都在Reserve之后”。下载、已处理重试和发送缓存同样经过锚门，不能绕过已知回滚或未决状态。`received` 先核验远端健康，再在读取正文的同一显式事务中重新比较完整head及本地门，事务结束后才返回正文。`inspect` 仅提供公开摘要及锚状态，不返回候选正文、完整密文或provider。
